================================================================
 WEAPON FORGE - HOW TO MAKE CUSTOM WEAPONS WITH JSON
================================================================

Weapon Forge lets you create new starting weapons for PUNK by
writing small JSON text files. No programming needed. The DLL does
the work; the JSON files are the weapons.

----------------------------------------------------------------
 1. HOW IT WORKS
----------------------------------------------------------------

When the loadout (ship select) screen opens, Weapon Forge:

  1. Looks in the "weapons" folder that sits next to
     WeaponForge.dll (inside BepInEx\plugins\...).
  2. Reads every *.json file in it.
  3. For each file it CLONES an existing game weapon (the
     "template"), then overwrites any stats you listed in the
     file. Everything you don't mention stays exactly like the
     template.
  4. Adds the result to the loadout list as a new starting ship.

Because your weapon starts life as a clone of a real game weapon,
it automatically gets that weapon's projectile model, particles,
sounds, and behavior class. Your JSON then bends it into whatever
you want: faster, meaner, homing, exploding, chaining, etc.

YES - editing the JSON is enough. Change a number, save, restart
the game, and the weapon behaves differently. The DLL never needs
to be rebuilt for stat/physics/property changes.

IMPORTANT: files are read at game startup (and when the loadout
screen loads). Edits made while the game is running do NOT hot-
reload - restart the game (or fully quit to desktop and relaunch)
to see changes.

SAVING MID-RUN: custom weapons are registered with the game at
startup, so you can save-and-quit with one equipped and use
"Continue" later without the load hanging. (This is why weapons are
read at startup, not only on the ship-select screen.) If you ADD or
RENAME a weapon file, then load an old save that had the old weapon
equipped, that old id won't exist anymore - keep a file around (same
"name") as long as any save still uses it.

----------------------------------------------------------------
 2. QUICK START
----------------------------------------------------------------

  1. Run the game once with WeaponForge.dll installed. The
     "weapons" folder appears next to the DLL with an example
     file (ExamplePopper.json) already inside.
  2. Copy ExamplePopper.json, rename the copy (MyGun.json).
  3. Open it in Notepad. Change "name" to something unique,
     change "displayName" to what you want on the menu card.
  4. Edit stats. Save. Launch the game.
  5. Your weapon is a new entry on the loadout select screen.

If something is wrong with a file, the game does not crash - the
weapon is skipped and the reason is written to:
     <game folder>\BepInEx\LogOutput.log
Search the log for "WeaponForge".

----------------------------------------------------------------
 3. FILE STRUCTURE
----------------------------------------------------------------

{
  "name": "MyGun",                <- REQUIRED. Unique internal id.
                                     Letters/numbers, no spaces.
  "displayName": "MY GUN",        <- Name shown on the menu card.
  "description": "It shoots.",    <- Card description text.
  "template": "Module Weapon White Popper",
                                  <- REQUIRED. Which game weapon to
                                     clone. Decides base behavior,
                                     projectile model, sounds. Can be
                                     a weapon module OR a raw weapon
                                     asset incl. enemy weapons (sec 4).
  "slot": "primary",              <- Optional. Where it equips:
                                     "primary" (left click, default),
                                     "secondary" (right click), or
                                     "gadget1"/"gadget2"/"gadget3"
                                     (the 1/2/3 keys). See section 4b.
  "source": "starter",            <- Optional. Where it can appear:
                                     "starter" (new-game pick, default),
                                     "loot" (drops from crates),
                                     "starterAndLoot" (both), or
                                     "none" (never offered - for helper
                                     weapons like subEmitter stages and
                                     turret ammo). See 4c.
  "lootWeight": 10,               <- Optional, loot only. Drop chance
                                     vs other crate modules (default 10).
  "shop": true,                   <- Optional. Buyable in the in-run
                                     shop. Independent of "source". 4d.
  "shopPrice": 150,               <- Optional, shop only. Cost in money
                                     (default 100).
  "shopUnlockLevel": 2,           <- Optional, shop only. Stations the
                                     player must unlock first (default
                                     1; 0 = from the first shop). 4d.
  "baseLoadout": "Starter_Popper",<- Optional. Which starting ship
                                     loadout to clone for the ship
                                     and module slots.
  "weapon": {                     <- Stat overrides for the weapon.
     ...see section 5...
  },
  "module": {                     <- Optional overrides for the
     ...see section 8...             module card (icon, color...).
  }
}

Rules of thumb:
- Anything you leave out keeps the template's value.
- Field names are not case-sensitive.
- A field name the game doesn't know logs a warning and is
  skipped (check the log if a change doesn't seem to apply).

----------------------------------------------------------------
 4. TEMPLATES - PICKING YOUR BASE WEAPON
----------------------------------------------------------------

The template decides the weapon's TYPE. There are four types, and
each type has its own extra fields (section 6).

PROJECTILE WEAPONS (bullets, machine guns, rifles, missiles):
  Module Weapon White Popper      - basic machine gun
  Module Weapon White Bolt        - rifle-style bolt
  Module Weapon White Dart        - homing dart (a MISSILE - see 6c)
  Module Weapon White Shotgun     - spread shot
  Module Weapon White Blades      - blades
  Module Weapon White Derbis      - debris chunks
  Module Weapon White DiscGun     - discs
  Module Weapon Purple Marbles    - bouncing marbles
  Module Weapon Purple Flack      - flak burst
  Module Weapon Purple Shard      - shards
  Module Weapon Purple Rocket     - MISSILE (see 6c)
  Module Weapon Caps Rocket       - MISSILE, caps resource (6c)
  Module Weapon Caps Flame        - flamethrower-ish
  Module Weapon Electron Rocket   - MISSILE, electric (6c)
  Module Weapon Electron Zapper   - electric chain projectile
  Module Weapon Electron Toroid   - electric toroid
  Module Weapon White Worm

HITSCAN WEAPONS (instant laser beams) - see 6d:
  Module Weapon Caps Laser
  Weapon Crawler Laser            - also melts terrain (cellConvertData)
  Enemy beams: Weapon_Fly_Laser, Weapon_Turret_Laser, Weapon_PhantomDrone,
  Weapon_Laser_CrossQueen, Weapon Unit CrossLaser / CrossRedLaser /
  CrossJockLaser, Weapon Laser CrossTablet, Weapon CrossPin, Weapon OneShot4

LOBBED / PHYSICS WEAPONS (objects that arc, tumble and bounce):
  Module Weapon White Derbis      - debris chunks
  Module Weapon Purple Flack      - flak burst
  Module Weapon Caps Loon
  Module Weapon Purple Can
  Module Weapon Purple ClusterCube
  Module Weapon Tech Dandelion    - (the "purple dandelion" - its
                                     real asset name is Tech)

  These are NOT a separate weapon type. Every one of them is an ordinary
  PROJECTILE weapon with "usePhysics": true, which makes it throw a
  physics object instead of a straight-flying shot. That means the whole
  projectile field set below applies to them - see section 6b.

MINION SPAWNERS (pet/drone weapons) - see 6e:
  Weapon Minion CrossSmallCaps
  Weapon Minion Cross Red
  Weapon Minion CrossRedBomber
  Weapon_Minion_CrossQueen
  Weapon FloaterOfficerCaps Mines
  (These are all raw ENEMY assets - they are the only true minion
  spawners in the game. NOTE: "Module Weapon Fly" is NOT one; it is an
  ordinary projectile weapon.)


ENEMY / RAW WEAPONS (advanced):
You can also use a raw weapon asset directly as the template, incl.
weapons enemies use. Examples:
  Weapon_Grunt          Weapon_Raven         Weapon_Zipper
  Weapon_Fly            Weapon_Fly_Laser     Weapon_PhantomDrone
  Weapon_Turret_Laser   Weapon_Turret_Worm   Weapon_CrossQueen
  Weapon Enemy Soldier  Weapon Enemy DroneMissile
  Weapon Enemy Queen Bomb   Weapon Enemy Turret Sniper
  Weapon Crawler Laser  Weapon FireBall      Weapon Fish
  Weapon Drone          Weapon BouncerRed
  Weapon Rocket Rookie  Weapon Rocket Soldier  Weapon SoldierPurple
Names come from the AssetRipper export (drop the ".asset"). Both
"Weapon_Name" and "Weapon Name" styles exist; use the exact name.
Most load fine; if one isn't in memory at the menu the log says so.

Enemy weapons are built to hurt the PLAYER, so on their own they'd
damage you, not enemies. Weapon Forge fixes this automatically:
"target" defaults to "enemies" (see section 4d), so an enemy weapon
you use will hit enemies and leave you alone. Set "target":"player"
if you actually want the original enemy behavior.

----------------------------------------------------------------
 4b. SLOTS - PRIMARY, SECONDARY & GADGETS
----------------------------------------------------------------

"slot" decides where the weapon equips:
  "primary"    left click (default) - replaces the ship's main gun
  "secondary"  right click
  "gadget1/2/3"  the 1, 2 and 3 keys

Weapons and gadgets are different MODULE TYPES, but you can mix them
freely - the "slot" you choose decides the final type, and Weapon
Forge converts as needed:
  - GADGET template + gadget slot  = the real gadget (its own
    behavior, e.g. Air Mine deploys mines). This is the normal way to
    make a gadget - pick one from the "Gadgets" group in the template
    list (section 4, "GADGET MODULES").
  - WEAPON template + gadget slot  = a gadget that fires that weapon
    (e.g. your custom rocket, on a key press).
  - GADGET template + weapon slot  = fires the gadget's weapon on
    left/right click instead of a key.

GADGETS fire on a key press with a cooldown, not held-down fire:
  - Cooldown  = 1 / fireRate  (higher fireRate = faster re-use)
  - Cost      = "cost" of "resourceUsed" per activation
  So set those weapon fields to tune how the gadget feels.
  - The loadout contains ONLY the weapon you make (plus the ship).
    A gadget loadout does NOT include the base loadout's popper on
    left-click - just your gadget.

GADGET MODULES you can use as a template:
  Module Active Purple AirMines    (air mines)
  Module Active Purple Surge       (surge)
  Module Active Purple Teardrop    (teardrop)
  Module Active Caps Igniter       (igniter)
  Module Active Caps Vial          (vial)
  Module Active Electron Circuit   (circuit)
  Module Active Generator Fuel     (fuel generator)

Example - use the real Air Mine gadget on key 1, buffed:
  {
    "name": "SuperMines",
    "template": "Module Active Purple AirMines",
    "slot": "gadget1",
    "weapon": { "damage": { "amount": 15, "damageType": "Purple" } }
  }

Example - turn a custom rocket into a gadget on key 1:
  {
    "name": "PocketRocket",
    "template": "Module Weapon Caps Rocket",
    "slot": "gadget1",
    "weapon": { "fireRate": 1.5, "cost": 3,
                "resourceUsed": "Resource White",
                "damage": { "amount": 20, "damageType": "White" } }
  }

----------------------------------------------------------------
 4c. SOURCE - STARTER WEAPON, LOOT DROP, OR BOTH
----------------------------------------------------------------

"source" controls where your weapon can show up:
  "starter"         only as a pick on the new-game loadout screen
                    (the default)
  "loot"            only as a drop - it appears inside the module
                    crates you smash open during a run, never on the
                    start screen
  "starterAndLoot"  both
  "none"            NEVER offered - not a start pick, not a drop. The
                    weapon is still BUILT and registered, so other things
                    can reference it by name ("Forge Weapon <name>"). This
                    is what you want for helper weapons: subEmitter stages
                    and turret ammo. ("shop" is a separate toggle and is
                    off by default, so "none" on its own = nowhere at all.)

HOW LOOT WORKS: a crate carries a LootDropper pointing at a DropTable,
and that table rolls exactly ONE module from a weighted pool (plus a
fixed pile of resources). The game already splits those pools by
element, which is what lets you pick WHICH crate your weapon comes
from. Resource/scrap-only tables are never touched.

"lootWeight" (default 10) is how likely your weapon is compared to
everything else IN THE SAME POOL. It is a plain weight, not a percent:
your odds are yourWeight / (poolTotal + yourWeight).

POOL SIZES DIFFER ENORMOUSLY, so the same weight behaves very
differently depending on lootFrom. Total weight already sitting in each
pool, and what a default 10 actually gets you:

    tech      total  50   ->  about 17%
    purple    total 161   ->  about  6%
    white     total 196   ->  about  5%
    caps      total 201   ->  about  5%
    queen     total 221   ->  about  4%  (but she drops 3 at once)

So a weapon at weight 10 is about THREE TIMES more likely to appear
from Tech crates than from any other. To be roughly as common in White
as in Tech you would need about weight 40.

Those are the odds on a FRESH run - the game shrinks a module's weight
as you collect copies of it (see lootRepeat), so pools thin out as a
run goes on.

"lootFrom" - WHICH CRATES. Leave it out (or use "all") and the weapon
drops from every pool, which is what "loot" has always meant. Give one
name, or a list, to restrict it:

    "lootFrom": "tech"
    "lootFrom": ["white", "caps"]

THE FIVE POOLS THAT ACTUALLY WORK:
  "white"    the plain CRATE. The biggest pool - 18 entries, including
             all 8 White weapons, boosters and augments. Also used by
             the CrossJock and CrossRed Bomber enemies.
  "caps"     CRATE CAPS (orange). 11 entries - Loon, Laser, Flame,
             Rocket, Igniter, burn augments.
  "purple"   CRATE PURPLE. 11 entries - Shard, Rocket, Marbles,
             ClusterCube, AirMines, Teardrop.
  "tech"     CRATE TECH. The SMALLEST pool at only 5 entries, so your
             weapon has the best odds of showing up here. Also used by
             the CRAWLER enemy.
  "queen"    a generic pool used only by the QUEEN, who drops THREE
             modules at once.
Aliases: "stamina"="white", "orange"="caps", "generic"="queen". The
full asset name (e.g. "DropGroup Modules Crate Tech") also works.

TWO MORE THE MOD *ADDS* A MODULE ROLL TO. Neither drops a module in the
base game, so naming one makes the mod append a NEW drop entry to that
crate. It is PURELY ADDITIVE - the crate keeps every one of its normal
contents and gains a module on top - and it only happens if a weapon
EXPLICITLY names the crate, so leaving lootFrom out never changes
anything.

  "level2"   CRATE LEVEL 2. It already has a 5-module pool wired up that
             the game never rolls, so this revives it: your weapon
             competes with those 5 stock regen/generator modules. That
             pool totals only 16, so a weight-10 weapon is about 38%.
             Arguably fixes an oversight in the game's own data.
  "money"    CRATE MONEY. No module pool exists anywhere for it, so the
             mod creates one. Only YOUR money-targeting weapons are in
             it, which means one of them ALWAYS drops from a money crate.
             That is strong - use lootWeight to balance between several,
             or pick a different crate if it is too generous.

WHAT IS STILL NOT AVAILABLE, AND WHY: the remaining crates roll no
module POOL and have nothing sensible to graft.

  CRATE GREEN is the BONUS / UPGRADE crate. It does not roll a pool - it
  always hands you exactly one "Module BoosterCore" (plus fuel and red
  resource). Those are the green modules with a little GRID PATTERN on
  them: park one beside your upgrade modules and everything inside its
  pattern gains +1 LEVEL, a real stat increase. Overlap two patterns on
  the same module and the bonuses STACK. Each BoosterCore randomly draws
  one of THREE shapes, it must be powered and connected to do anything,
  and it only lifts modules flagged "canBeBoosted" (boosters cannot
  boost each other). Weapons and gadgets benefit too - a levelled drone
  gadget raises its drone cap, for example.
  The six BOX pickups each drop one fixed item.

If you name any of these, it is refused with an explanation in the log
rather than silently never dropping.

ENEMIES: four enemies really do roll a module pool, and they SHARE the
crate pools rather than having their own - Crawler uses tech, CrossJock
and CrossRed Bomber use white, and the Queen has her generic one. So
targeting "tech" also means "drops from Crawlers". Every other enemy
drops resources only; making one of those drop a module needs a change
we have not built yet.

"lootRepeat" - ALLOW DUPLICATES. By default a weapon you already own
stops dropping, and that is the GAME's rule rather than ours: every
module carries a "repeatedDropChanceMultiplyer" that multiplies its
drop weight once for each copy you already have, and 120 of the ~145
stock modules set it to 0 - so one copy takes it to zero weight for the
rest of the run.

    "lootRepeat": true     keep dropping at full chance, forever
    "lootRepeat": 0.5      each copy you own halves the odds of the
                           next, so duplicates get rarer but never
                           impossible
    "lootRepeat": false    the stock once-per-run behaviour (default)

This is set on a private clone of your module, so it can never make a
stock weapon start repeating.

"repeatInShop" (inside the "module" block) is the SHOP twin of
lootRepeat: true lets the shop stock the weapon more than once in a run.
Off by default, because the game drops a module from the pool once you
have bought or picked one up.

    "module": { "repeatInShop": true }
MAKING DUPLICATES WORTH FINDING. Pair "lootRepeat" with a RANGE on
"powerNodes" (inside the "module" block) and the power-core cap is
ROLLED PER DROPPED COPY:

    "lootRepeat": true,
    "module": { "powerNodes": { "min": 1, "max": 8 } }

The Weapon Builder page has "power nodes: min" and "power nodes: max"
fields for this, so you do not have to hand-edit - fill either in and it
writes the range for you. (Filling in the plain "power nodes (fixed)"
field as well is fine; the range wins and the page warns.)

That is the game's own behaviour, not something added: Module's
constructor does Random.Range(powerLevel.Min, powerLevel.Max), and
every dropped pickup is created through ModuleData.DeepCopy(), so each
copy gets its own roll. The pickup SHOWS the rolled number on the
ground before you pick it up (hover reads "MAX POWER CORES: N"), the
value stays with that copy, and it survives save/load. So finding the
same weapon again is a chance at a better one.

The roll is UNIFORM though - an 8 is exactly as likely as a 1. Making
high caps genuinely rare would need new code.

NOTE: loot and starter both still register the weapon at startup
(so saves keep working). "loot" just hides it from the start screen.
"source" does NOT affect the SHOP - that is the separate "shop" toggle
below (with "shopPrice" and "shopUnlockLevel"), which IS supported and
off by default.

Example loot-only weapon:
  {
    "name": "RareCannon",
    "displayName": "RARE CANNON",
    "template": "Module Weapon Purple Rocket",
    "source": "loot",
    "lootWeight": 5,
    "weapon": { "damage": { "amount": 30, "damageType": "Purple" } }
  }

----------------------------------------------------------------
 4d. TARGET - WHO THE WEAPON HURTS
----------------------------------------------------------------

"target" controls whether the weapon damages enemies or the player:
  "enemies"  (default) hits enemies and leaves you unharmed
  "player"   hits the player (the original enemy-weapon behavior)

WHY THIS EXISTS: in PUNK a projectile only hits things on a matching
physics "layer", and enemy weapons put their shots on an enemy layer
that only collides with the PLAYER. So an enemy weapon used as-is
would damage you, not enemies. With "target":"enemies" Weapon Forge
re-lays the cloned projectile onto the player-projectile layer (and
sets a beam's hit mask to enemies), which makes it hit enemies AND,
because of how the layers work, automatically stops it hitting you.

Notes:
  - Normal player-weapon templates are already "enemies", so the
    default changes nothing for them.
  - Works for projectile, beam (hitscan), and physics weapons.
  - Does NOT apply to minion/pet weapons - a summoned minion has its
    own faction, which this option doesn't change.

Example - an enemy fireball that now hurts enemies:
  {
    "name": "MyFireball",
    "displayName": "FIREBALL",
    "template": "Weapon FireBall",
    "target": "enemies",
    "weapon": { "damage": { "amount": 8, "damageType": "Caps" } }
  }

----------------------------------------------------------------
 4e. SHOP - BUYING THE WEAPON IN A RUN
----------------------------------------------------------------

Set "shop": true to make the weapon purchasable in the in-run shop.
This is INDEPENDENT of "source" - a weapon can be a starter pick, a
loot drop, AND a shop item all at once (or shop-only).

  "shop": true              enable shop purchase
  "shopPrice": 100          cost in money/yellow (default 100)
  "shopUnlockLevel": 1      how many STATIONS you must unlock before it
                            can appear (default 1)

HOW PUNK'S SHOP UNLOCK WORKS (from the game's code): the shop is
gated by a STATION THRESHOLD, not pure chance. There's one counter
that is both "stations unlocked" and "shop tier". Every time you
unlock a station, the game rolls the next tier of shop items. So:
  shopUnlockLevel: 0  -> can appear in the very first shop (before any
                         station is unlocked)
  shopUnlockLevel: 1  -> after you unlock your 1st station (default)
  shopUnlockLevel: 3  -> after your 3rd station
Stock weapons live around tiers 1-5, so 1-3 feels natural.

Unlike stock weapons (which share a big weighted pool and only MIGHT
appear), a Weapon Forge shop weapon is added as its own guaranteed
entry - once you reach its tier it WILL show up (as long as you don't
already own it).

Notes:
  - A price is required internally; Weapon Forge sets one up for you
    (in money), so it never crashes the shop.
  - Each shop tier is rolled ONCE as you pass it, so if you're already
    past "shopUnlockLevel" when the file is added, it won't retro-
    appear that run - start a new run to see it.

Example - a mid-game shop weapon:
  {
    "name": "ShopBlaster",
    "displayName": "SHOP BLASTER",
    "template": "Module Weapon White Bolt",
    "shop": true,
    "shopPrice": 175,
    "shopUnlockLevel": 2,
    "weapon": { "damage": { "amount": 6 } }
  }

----------------------------------------------------------------
 4b. ELECTRIC / CHAIN-LIGHTNING WEAPONS (the White Tesla)
----------------------------------------------------------------

A hitscan/laser weapon can fire chain lightning like the White Tesla.
See ExampleWhiteTesla.json - it's the classic White Tesla as an editable
weapon (and, unlike the old standalone WhiteTeslaMod, it's save-safe).

These are TOP-LEVEL keys (not inside "weapon"):
  "dischargeOnFire": true   Makes the weapon fire a chain-lightning
                            DISCHARGE from the ship (hitscan guns don't do
                            this on their own). REQUIRED for lightning.
  "chainThroughEnemies": true  Lets the lightning hop enemy-to-enemy
                            (default true when dischargeOnFire). Adds a
                            conductor to every enemy - only happens if you
                            actually have an electric weapon.
  "buildupSeconds": 2       Telegraph time before the strike lands.
  "hideBeam": true          Hide the base laser beam so only the lightning
                            shows (the Tesla look).
  "lightningColor": "rainbow"  Recolor the lightning: a color name / #hex,
                            or "rainbow" for an RGB cycle. NOTE: the lightning
                            beam is shared, so this is global (all your
                            chain lightning), and the last electric weapon
                            loaded wins. Leave it out for the stock
                            white/blue look.
  "lightningRgbSpeed": 0.5  Rainbow only: hue cycles per second.
  "lightningRange": 20      How FAR the lightning reaches / arcs PER HOP -
                            the real "charge range". This is the one knob
                            that actually changes reach. It is NOT
                            chainLength (that's the NUMBER of hops) and NOT
                            the weapon's hitscan range (that's the hidden
                            laser beam). The game normally uses one global
                            reach for all electricity; this overrides it for
                            PLAYER lightning only (enemy electric attacks
                            keep their reach). It's shared across all your
                            chain weapons - last one loaded wins. Bigger
                            values = longer arcs but more chain math.

The actual lightning DAMAGE/reach lives in the weapon's discharge block:
  "weapon": { "discharge": { "damage": { "amount": 3,
                "damageType": "Resource White" },
              "chainLength": 6, "subSystem": "Player" } }
  - chainLength = how many enemies the arc hops.
  - subSystem MUST be "Player" for a visible player-side beam.
  - Damage is the discharge amount ticking over the strike window, so
    total damage = amount x ticks x chain - tune by feel, not 1:1.
Set the weapon's own "damage": { "amount": 0 } if you want ALL damage to
come from the lightning (like the Tesla).

----------------------------------------------------------------
 4c. ORBIT / SATELLITE WEAPONS (projectiles that circle you)
----------------------------------------------------------------

Turns a weapon's projectiles into a ring that orbits your ship. See
ExampleOrbitRing.json (based on the White Worm). Works in a WEAPON slot
(primary/secondary) AND in a GADGET slot (see the gadget note below).
These are TOP-LEVEL keys (not inside "weapon"):

  "orbit": true             REQUIRED - makes this an orbit weapon.
  "orbitMode":              how it runs:
     "passive"  always spinning while equipped (default)
     "hold"     spins only while you hold fire (drains resource/sec if
                orbitHoldDrainPerSecond is set)
     "toggle"   tap fire to turn the ring on/off
     "fire"     tap fire to (re)summon the ring for orbitFireDuration sec

  GADGET SLOTS (gadget1/2/3, the 1/2/3 keys): orbit works here too, but a
  gadget is PRESS-activated (it has no "held" or always-on fire like a
  primary weapon), so the modes map to the gadget key like this:
     "toggle"          press the gadget key to turn the ring on/off
     "passive"/"hold"  same on a gadget - press to turn on, press to turn off
                       (a gadget can't be truly always-on, so it needs the
                       first press anyway; a second press switches it off)
     "fire"            press to summon the ring for orbitFireDuration seconds
  So on a gadget, every mode except "fire" is a simple on/off toggle. A
  primary/secondary orbit still respects passive/hold/toggle as described
  above - this only changes how gadgets behave.
  "orbitDirection": "cw" or "ccw"   spin direction (default cw).
  "orbitRadius": 3          circle size - how far the orbs sit from you.
                            With several rings this is the INNERMOST ring.

  MULTIPLE RINGS (nested rings around the ship):
  "orbitRings": 3           how many concentric rings (default 1).
  "orbitRingMode":          how projectileCount is used:
     "split" (default) the count is SHARED across the rings, dealt out
              round-robin so they stay even. Adding rings re-arranges the
              orbs you already have instead of making more.
     "full"   EVERY ring gets the full count, so you end up with
              projectileCount x rings orbs.
  "orbitRingSpacing": 1.5   gap between one ring and the next, world units.
  "orbitRingStagger":       where the orbs sit within each ring:
     "auto" (default) offsets each ring by half a slot so the orbs
              interleave rather than lining up
     "aligned" all rings share the same angles - orbs form spokes
     a number  degrees of offset added per ring (e.g. 15)
  "orbitRingAlternate": true  flip the spin direction on every other ring,
                            giving counter-rotating rings.
  "orbitRingSpeedStep": 0.6  speed multiplier applied per ring outward.
                            1 = every ring spins together; 0.6 = each ring
                            out is 60% the speed of the one inside it;
                            above 1 = outer rings whip round faster.
  Rings work with everything else: contact damage, blocking, destructible
  orbs + regen, and the spiral modes (each ring spirals out to its own
  radius).
  "orbitSpeed": 140         spin speed in degrees/second.
  "orbitContactDamage": true  orbs damage enemies they touch (default true).
  "orbitWeaponEffects": true  default true. An orb hit delivers the weapon's
                            WHOLE payload, not just raw damage: burn, the
                            "got attacked" reaction (aggro), kill credit,
                            and the weapon's explosion + discharge/lightning
                            are spawned where the orb touched. Set false for
                            plain contact damage only. NOTE the explosion and
                            discharge fire on every damaging contact, so they
                            follow orbitDamageRepeatDelay - raise that if a
                            big explosion feels too spammy.
  "orbitDamageRepeatDelay": 0.3  seconds before an orb can re-hit the SAME
                            enemy (stops instant melt).
  "orbitBlockProjectiles": true  orbs shoot down enemy BULLETS they touch,
                            turning the ring into a shield. The catch radius
                            is orbitHitRadius - a very fast enemy shot can
                            slip between two orbs in one frame, so widen
                            orbitHitRadius (or add orbs) if things get
                            through.
  "orbitPushForce": 0       shove enemies away on contact (0 = off). Set
                            contactDamage false + a push for a pure shield.
  "orbitPulse": 0           radius breathes in/out by this much (0 = off).
  "orbitSpinUp": 1          seconds to ramp from still to full spin.
  "orbitFling": true        tapping fire makes the orbs surge outward then
                            snap back (a burst attack).
  "orbitSuppressFire": true default true = a pure orbit (no forward shots).
                            false = ALSO fire the weapon normally.
  "orbitHitRadius": 0.6     how big each orb's contact area is.
  "orbitVisual": "Ammo_Worm"  which projectile art to use as the orbs
                            (default: the weapon's own projectile).

  TERRAIN (optional):
  Orbs are NOT real projectiles - they're art positioned every frame, with
  their colliders switched off - so they have no collision layer of their
  own and there is nothing to "put on the projectile layer". By default they
  simply pass over walls. That is not phasing, and the phasing flag has no
  effect on them either way. Two separate switches control terrain:
  "orbitDamageTerrain": true  orbs DIG. Each touch is handed to the level as
                            a real projectile hit, so the cell takes the
                            weapon's damage, shakes, catches fire from the
                            weapon's burn, and breaks if the damage beats the
                            cell's resistance - the same rules a normal shot
                            plays by, so a weak orbit won't bore through
                            tough rock. The weapon's explosion/discharge are
                            NOT re-spawned per dig tick (that would be a
                            continuous blast); they still fire on enemy hits.
  "orbitTerrainRepeatDelay": 0.15  seconds between cell hits PER ORB. One orb
                            breaks at most one cell per tick, so this is
                            your dig speed. Lower = faster tunnelling.
  DESTRUCTIBLE ORBS (optional):
  "orbitDestroyOnEnemy": true   orb is destroyed when it hits an enemy.
  "orbitDestroyOnTerrain": true orb is destroyed when it touches terrain.
                            This kills the ORB - it does not hurt the wall.
                            Combine with orbitDamageTerrain for an orb that
                            punches one hole and pops, and orbitRegenMode to
                            bring it back.
  "orbitRegenMode":         how a destroyed orb comes back:
     "both"  timer AND on fire/toggle (default)
     "timer" only after orbitRegenTime seconds (best for passive)
     "fire"  only when you fire / re-toggle the weapon (active modes)
  "orbitRegenTime": 3       seconds to respawn a destroyed orb (timer).
  "orbitPopExplosion": true destroyed orb bursts - a small AoE hit at the
                            spot it died.
  "orbitPopRadius": 1.5     size of that burst.

  SPIRAL OUTWARD (orbs travel out instead of holding a ring):
  "orbitSpiral":            how the orbs move outward (default "off"):
     "off"    classic fixed-radius ring (the default).
     "launch" orbs spiral OUT from the ship, then detach at the outer edge
              and fly straight off toward enemies - they do NOT come back,
              then respawn from the center. A "vortex cannon".
     "sweep"  orbs spiral out to the edge and reset to the center, over and
              over - a continuous rotating-sprinkler sweep. They never leave,
              they just don't orbit back around.
     While spiraling, orbitRadius is the OUTER edge, and orbitPulse/orbitFling
     are ignored. Contact damage / destroy / regen still work as above.
  "orbitSpiralInner": 0.4   radius the spiral STARTS at (near the ship).
  "orbitSpiralTime": 0.8    seconds to spiral from inner to outer.
  "orbitSpiralLaunchSpeed": 12  fly-off speed once launched ("launch" mode).
  "orbitSpiralRange": 14    how far a launched orb travels before it recycles.
  See ExampleSpiralVortex.json.

HOW THE NUMBERS MAP (per your request):
  - projectileCount (in the "weapon" block) = the NUMBER of orbs, evenly
    spaced (4 = N/E/S/W). It's read LIVE, so +projectile modules add orbs
    and auto-respace them.
  - damage (in the "weapon" block) = damage per contact hit, read live so
    +damage modules scale it.
  - orbitRadius = circle size; orbitSpeed = rotation speed; orbitDirection
    = which way it spins.

----------------------------------------------------------------
 4d. SUB-EMITTERS (a shot that fires another WEAPON when it ends)
----------------------------------------------------------------

"subEmitter" (inside "weapon") names ANOTHER weapon that gets fired at
the spot where this shot dies - cluster bombs, flak bursts, shrapnel.
It's a stock game field, so it works with no extra mod support. Big
thanks to the PUNK Discord for surfacing this one.

  "weapon": {
    "subEmitter": "Forge Weapon White Popper Sub",
    "rangeData":        { "enabled": true, "destroyWhenReached": true,
                          "fireSub": true },
    "impactBehaviour":  { "enabled": true, "fireSub": true }
  }

FOUR THINGS THAT MATTER:

1. NAMING. For one of YOUR WeaponForge weapons the name is
   "Forge Weapon " + the "name" field of its .json. So a sub whose
   json says "name": "White Popper Sub" is referenced as
   "Forge Weapon White Popper Sub". (Stock weapon asset names work too.)

2. IT NEEDS A TRIGGER. Setting subEmitter alone does nothing - the sub
   only fires where you set "fireSub": true:
     rangeData.fireSub        when the shot reaches max range
                              (STRAIGHT shots only - a LOBBED
                              shot has no range trigger at all,
                              see below)
                              (also needs enabled + destroyWhenReached)
     lifetimeData.fireSub     when the shot's timer runs out
     impactBehaviour.fireSub  on impact - works on ENEMIES AND TERRAIN
                              (also needs enabled; an impact closer than
                              impactBehaviour.safetyDistance is ignored,
                              the shot just bounces - that's usually why
                              a terrain test "does nothing")

3. SUBS FIRE STRAIGHT UP. The sub is fired from the dead shot's position
   with a fixed UPWARD direction - it does NOT inherit the parent's
   heading. Give the sub weapon "spread": 360 (plus a few
   projectileCount) so it bursts outward like shrapnel.

4. CHAINING. A sub can have its own subEmitter, so chains nest as deep
   as you like.
   FILE ORDER NO LONGER MATTERS. subEmitter names are now resolved AFTER
   every weapon file has been built, so a sub may live in a file that
   sorts before or after the weapon using it. (It used to matter, and it
   failed silently: "cocktail.json" sorts before "cocktailFlame.json", so
   the cocktail looked for a flame that did not exist yet and quietly got
   none. If you see an older guide telling you to prefix files 00_, 01_,
   that is why - it is no longer needed, though it does no harm.)
   You can also just use the sub's own "name": both
     "subEmitter": "Cocktail Flame"
     "subEmitter": "Forge Weapon Cocktail Flame"
   resolve to the same weapon. Stock weapons use their asset name, e.g.
   "Weapon Caps Flame".
   WARNING: a chain that loops back on itself (A -> B -> A) will hang
   the game on load. Keep chains one-way. A sub pointing at ITSELF is
   caught and ignored with a warning.

HIDING THE HELPER SUBS: a sub weapon works even if you can never obtain
it, so keep them out of your runs with "source": "none".

Sub weapons are fired directly, so they DON'T charge their "cost" - set
the parent weapon's cost for balance instead.

----------------------------------------------------------------
 4e. TURRET / MINE (a shot that keeps firing WHILE it's alive)
----------------------------------------------------------------

subEmitter (4d) only fires when a shot DIES. "turret" makes a projectile
fire another weapon over and over WHILE IT LIVES, and optionally hurt
anything touching it. Classic use: a disc that glides to a stop, sprays
for a few seconds, then vanishes. See ExampleTurretDisc.json (+ its ammo
ExampleTurretShot.json). TOP-LEVEL keys:

  "turret": true            REQUIRED. Projectile weapons only (NOT
                            usePhysics/lobbed).
  "turretWeapon": "..."     REQUIRED. The weapon fired each volley. For
                            your own weapons that's
                            "Forge Weapon " + its "name" field. Looked up
                            at RUNTIME, so unlike subEmitter the file
                            LOAD ORDER DOESN'T MATTER.
  "turretInterval": 0.5     seconds between volleys.
  "turretDelay": 0.8        seconds before the FIRST volley - set this to
                            about the flight time so it starts shooting
                            once it has settled into place.
  "turretAim":              how each volley is aimed:
     "rotate"  (default) sweeps around, making a spiral
     "nearest" auto-targets the closest enemy; holds fire if none
  "turretRotation": 140     sweep speed, degrees/second ("rotate").
                            0 = always fires the same direction.
  "turretDirection": "cw"   or "ccw" - sweep direction.
  "turretStartAngle": 0     angle of the first volley ("rotate").
  "turretRange": 12         target search radius ("nearest").
  "turretContactDamage": true  MINE behaviour - enemies touching it take
                            this weapon's damage, and the disc does NOT
                            die or explode.
  "turretContactRadius": 0.6   touch radius.
  "turretContactDelay": 0.4    seconds before the SAME enemy is hurt again.

FIRING IS FREE: volleys spend no resource (the cost is charged when YOU
pull the trigger, not by the turret). Balance with the parent's "cost".

MAKING IT HOVER (in the "weapon" block):
  "rangeData": { "enabled": true, "range": 5, "slowDown": true,
                 "destroyWhenReached": false }
        slowDown eases it to a dead stop; destroyWhenReached:false keeps
        it alive sitting there.
  "lifetimeData": { "enabled": true, "time": 4 }     how long it lasts.
  "impactBehaviour": { "enabled": false }            so bumping something
        doesn't kill it.
  "projectileBounceData": { "enabled": true, "layerMask": ["Ground"] }
        optional - ricochet off walls on the way out. NOTE: "enabled" on
        its own does nothing; most templates ship an EMPTY layerMask, so
        you must list the layers to bounce off.
  Do NOT give it a "pierceLimit" - the pierce cap would delete it.

SET FOR YOU AUTOMATICALLY (so the thing actually behaves):
  * The turret OWNS contact damage, so the projectile's own collision
    damage is zeroed out - otherwise every touch would be counted twice,
    on two different cooldowns.
  * Piercing is switched on. Without it the game snaps the projectile
    onto whatever it touches, so enemies would shove your "hovering"
    disc around the room. Walls still stop (or bounce) it.
  * If the weapon has NO way to expire (no lifetime, no
    destroyWhenReached, no impact), a lifetime is forced - otherwise
    every shot would leave a permanent turret behind.
  * "turret" is ignored on an orbit weapon, and a turret is not allowed
    to fire itself (both would multiply without bound).

WHY CONTACT DAMAGE IS HANDLED BY THE TURRET: a projectile collides by
sweeping along its own movement, so once it stops dead it may detect
nothing at all. The turret does its own radius check every frame, so a
parked mine still damages what touches it - and because it owns the
damage there's exactly one hit per contactDelay.

----------------------------------------------------------------
 5. WEAPON FIELDS - ALL WEAPON TYPES
----------------------------------------------------------------

These go inside the "weapon": { } block and work on every type.

  "damage": { "amount": 3, "damageType": "Resource White" }
      Contact damage per hit and its element/resource type.
  "fireRate": 5             Shots per second.
  "warmupTime": 0.5         Seconds of holding fire before the
                            first shot (charge-up).
  "damageRepeatDelay": 0.1  HITSCAN / LASER weapons ONLY (e.g. the Caps
                            Laser): seconds between damage ticks on a
                            target you're holding the beam on. Lower =
                            damages faster. Default 0.25 (4 ticks/sec).
                            NOTE: also gated by fireRate - the beam only
                            re-checks for damage each "shot", so keep
                            fireRate high enough to hit your intended tick
                            rate.
                            It is not a field on any other weapon type, so
                            on a projectile weapon it is SILENTLY DISCARDED
                            (the log still says the weapon built fine).
                            Projectiles have their own, inside
                            "piercingData": { "damageRepeatDelay": ... }.
  "burstSize": 3            Shots per trigger pull (burst fire).
  "burstDelay": 0.08        Seconds between burst shots.
  "projectileCount": 5      Projectiles per shot (shotgun!). It is a
                            FLOAT and rounds UP in effect: 2.5 fires 3.
  "spread": 30              Total width of the evenly-spaced fan, in
                            degrees. IGNORED ENTIRELY when
                            projectileCount is 1 - see 6a. Use 360 for a
                            full ring (that value is special-cased so
                            two shots don't land on the same angle).
  "angleVariance": 4        Random inaccuracy in degrees, applied per
                            shot. THIS is the knob for a single-shot
                            weapon's accuracy, not "spread".
  "angleOffset": 0          Rotates the whole firing pattern.
  "knockbackForce": 2       Recoil pushing YOUR ship backward.
  "pushForce": 1            Force applied to whatever you hit.
  "resourceUsed": "Resource White"
                            Which ammo tank the weapon drains.
                            (White/stam, Caps/orange, Purple,
                             Electron...)
  "cost": 0.5               Ammo drained per shot.
  "barrelLength": 0.5       How far from the ship shots spawn.
  "explosion": {
      "radius": 2,
      "damages": [ { "amount": 4, "damageType": "Resource Caps" } ],
      "sfx": "6d3022f0-9b78-4030-b8a7-ac9468466f59",
      "skipCamShake": true
  }
      NOTE "damages" is a LIST, and it also picks the visuals: entry 1
      chooses the base explosion art and each extra entry layers that
      element's add-on art on top. So a two-entry list is the ONLY way to
      get a mixed-element blast. NEVER leave it empty while radius > 0 -
      the game reads entry 1 unconditionally and errors.
      "sfx" is the boom, as an audio GUID (see SOUND below).
      "skipCamShake": true stops the blast shaking the camera - the fix
      for a fast-firing explosive turning the screen to mush. This shake
      is separate from "shakePreset": the explosion one is auto-scaled by
      radius and can only be suppressed, never swapped.
  "discharge": {            Chain lightning burst (needs a
      "damage": { "amount": 3, "damageType": "Resource White" },
      "chainLength": 5,        trigger - see lifetimeData /
      "subSystem": "Player",   impactBehaviour "discharge": true)
      "layerMask": "Entities"
  }
      "layerMask" is which layers the lightning may hop to. Every stock
      weapon uses "Entities" (enemies). Accepts a name, a list of names,
      or a raw bitmask number. WARNING: a misspelled layer name silently
      becomes "hits nothing" - nothing warns you, so copy it exactly.
  "aimAssistData": { "enabled": true, "maxAngle": 15,
                     "isPredictive": true }

  SOUND, SHAKE & MUZZLE - every stock weapon sets most of these, and
  until now a forged weapon just inherited whatever its template had.
  All of them point at something the game already ships: sounds by audio
  GUID, everything else by asset NAME. A value the game doesn't know is
  skipped silently, so use the builder's pickers.

  "shootSfx": "d39fd50f-9e3e-41ef-9ccd-f00c2282dbb1"
                            The firing sound, once per volley. The only
                            sound field that works in EVERY slot -
                            primary, secondary, gadget AND sub-emitter
                            stages. Must be the GUID: the lookup compares
                            GUIDs only, so "Weapons/Bolt/Shoot" is
                            silence. Handy ones:
                              Popper   891a1b2e-39c4-4a79-bcc9-6b89523a429d
                              Bolt     d39fd50f-9e3e-41ef-9ccd-f00c2282dbb1
                              Shotgun  3c33af41-a69f-48ef-bfad-4dfc832c3ed0
                              Worm     0a935746-47fa-4289-8e15-85cdc9654830
                              Blades   9eb980c5-e062-4bd2-8542-ab006384856f
                              Derbis   819a0502-ee97-4cae-ac1b-9b1f5a25e2b3
                              Marbles  b4f0a35e-3bd1-458f-a672-c0aed298c6eb
                              Dart     3da1c704-cb77-4f4a-9b07-91849362b2bd
                              Toroid   2006c890-c2b5-460d-93fa-ea8ff10dc66d
                              Laser    b64bac2d-d394-4d46-a5a3-343333b65a51
  "reloadSfx": "c3120d6d-d216-4f5b-b6ad-36229edbc203"
                            Plays when the cooldown ends. 79 of the 80
                            stock projectile weapons use this exact one.
  "continousShootSfx"       A LOOPING sound while you hold fire, for
  "startSfx"                beams and flamethrowers, plus the one-shots
  "releaseSfx"              for spin-up and spin-down. Only Flame and
                            Laser use them in stock. Yes, the game
                            really spells it "continous". These are
                            primary/secondary only - a gadget never
                            starts the loop. GOTCHA: releaseSfx only
                            fires if the loop actually started, so never
                            write "continousShootSfx": null and expect a
                            release sound - just omit the field.
                              Flame  shoot c63c92e3.. is START,
                                     loop  e8fc5ecf.., release 0b773c09..
  "warmupSfx": "ea8fb19f-4770-4b84-b478-95d30b805d6e"
                            Charge-up sound; pair with warmupTime. No
                            stock projectile weapon sets it (that GUID is
                            the Laser's).
  "shakePreset": "Shake_Gunshot_Small"
                            Screen shake per shot. You can only SWAP
                            presets, never tune one. Options:
                            Shake_Gunshot_Small (33 stock weapons),
                            Shake_Gunshot_Medium, SmallExplosion,
                            Shake_Explosion, Shake_Explosion_MIN,
                            Shake_Explosion_Long, Shake_Explosion_MAX,
                            Shake_Collision, Shake_Excavate,
                            Shake_Wound, Shake_Shipdamage.
                            Two warnings: it comes from the ship's
                            shooter, so a GADGET-slot weapon never
                            shakes; and high fireRate +
                            Shake_Explosion_MAX is genuinely
                            unplayable.
  "rumblePreset": "Rumble WeaponShot Small"
                            Gamepad rumble per shot. Same gadget
                            limitation, and inert on keyboard/mouse.
                            Options: Rumble WeaponShot Small (43 stock),
                            Medium, Large, Derbis, Flame.
  "muzzleParticlePrefab": "MuzzleParticle Popper"
                            Flash at the barrel. One instance is
                            pre-made per projectile, so a big
                            projectileCount with a heavy prefab costs
                            performance. Options: MuzzleParticle Popper
                            (53 stock), PopperRed, Fly, Beacon, Sniper,
                            Cross, CrossAlpha.
  "muzzleColor": "#33ddff"  Recolor that flash. Same value styles as
  "muzzleRgbSpeed": 0.5     projectileColor: hex (#rrggbb or #rrggbbaa),
                            an HTML color name ("cyan"), a game color
                            ("ColorBlue"), or "rainbow" / "rgb" for an
                            animated cycle (muzzleRgbSpeed = hue cycles
                            per second, default 0.5, negative to cycle
                            backwards, kept separate from rainbowSpeed so
                            the flash and the shot can cycle at different
                            rates). A flash lives a fraction of a second,
                            so a slow rainbow reads as "every shot is a
                            slightly different color" rather than as a
                            visible cycle - raise the speed if you want
                            the flicker itself to rainbow.

                            HOW IT WORKS, because it matters: a muzzle
                            flash has no single "color" field. Its color
                            lives in the particle system's startColor,
                            and the stock ones store it as a RANDOM COLOR
                            picked along a gradient that runs white ->
                            transparent - that random pick is what makes
                            the flash flicker. Both the prefab root AND
                            its child (Particle_muzzleFlash2) have their
                            own. So muzzleColor MULTIPLIES that gradient
                            instead of replacing it: the flicker and the
                            fade-out survive, and only the hue changes.
                            Consequences:
                              - a DARK value dims the flash rather than
                                darkening it. Use bright hues.
                              - pure white does nothing (x1).
                              - alpha in a hex value (#rrggbbaa) scales
                                the flash's own alpha, so #ffffff80 is a
                                half-strength flash.

                            ONE MORE WRINKLE: four of the muzzle prefabs -
                            PopperRed, Laser, LaserRed and CrawlerLaser -
                            also bake a COLORED fade into the particle
                            (colorOverLifetime: white -> red, or -> blue),
                            and Unity multiplies that into startColor. Left
                            alone, cyan x red = black, so a tinted PopperRed
                            flash would mostly vanish. So tinting first
                            drains that baked ramp of hue, keeping only its
                            brightness curve: you get your color with the
                            prefab's fade shape. The upshot is that tinting
                            PopperRed no longer looks red at all - that was
                            the point - and the seven prefabs with no
                            colored ramp are unaffected either way.
                            The prefab is SHARED by 53 stock weapons, so
                            the mod tints a private clone - your weapon
                            can never recolor anyone else's flash.
                            Needs a muzzleParticlePrefab to exist (the
                            template's own counts); if there is none you
                            get a warning in the log and nothing else.
  "reloadParticlePrefab": "reloadParticle_weapon_Popper"
                            Puff when the weapon comes off cooldown.
                            Only 9 stock weapons bother, all with this
                            one.
  "projectileSprite": "myBullet"
                            YOUR OWN ART instead of the game's. Put a PNG in
                            the "sprites" folder next to the DLL and name it
                            here. Projectile weapons only for now (a beam's
                            art is stretched and tiled, which needs 9-slice
                            borders - not wired up yet).

                            EASIEST WAY: open "Sprite Sheet Builder.html"
                            (ships beside the weapon builder). Drop your PNG
                            in, drag boxes / auto-detect / grid-slice, and it
                            writes the .json for you. It also converts a GIF
                            into a PNG sheet, because the engine cannot read
                            GIF at all.

                            BY HAND: drop "myBullet.png" in the sprites
                            folder and that whole image becomes a sprite
                            called "myBullet". For several sprites out of one
                            sheet, add a .json beside it:
                              { "sheet": "myart.png",
                                "pixelsPerUnit": 20,
                                "sprites": [
                                  { "name": "myBullet",
                                    "x": 0, "y": 0, "w": 8, "h": 8 } ] }

                            *** NAMING - the one everybody trips on ***
                            This key takes the name of a THING INSIDE the
                            sheet, never the .png or .json filename. A sheet
                            holds two kinds of named thing:
                              sprites    still frames. The slicer names them
                                         <sheet>, <sheet>_1, <sheet>_2 ...
                                         (those numbers only keep the names
                                         unique - they are NOT frame numbers)
                              animation  the flipbook. The slicer names it
                                         <sheet>Anim
                            So for petrolbm.png:
                              "projectileSprite": "petrolbm"      -> ONE
                                                  frozen frame
                              "projectileSprite": "petrolbmAnim"  -> the
                                                  animation
                            Both are legal, so the mod cannot reject either -
                            but it now logs a hint when you name a frame that
                            is also frame 1 of an animation. The slicer's
                            export panel always shows the exact line to paste
                            and prefers the animation when there is one.

                            ANIMATED: add an "animations" block and point
                            projectileSprite at the ANIMATION's name - the
                            key is the same, and the mod works out whether a
                            name means a still sprite or a flipbook:
                              "animations": [
                                { "name": "spinBullet",
                                  "fps": 12,
                                  "loop": "loop",
                                  "randomStart": true,
                                  "frames": [ "f0","f1","f2","f3" ] } ]
                              frames      play order, taken from THIS array
                                          and nothing else. The "_1"/"_2"
                                          numbers the slicer adds to
                                          auto-named sprites only keep names
                                          unique - they are NOT frame
                                          numbers, and renaming a sprite
                                          does not reorder anything.
                              fps         frames per second. 0 or less just
                                          shows the first frame.
                              loop        "loop" (default) / "once" (stops
                                          on the last frame) / "pingpong".
                              randomStart every shot starts on a random
                                          frame. Turn this ON for a shotgun:
                                          otherwise all ten pellets flip in
                                          lock-step and read as one strobe
                                          rather than ten spinning bullets.
                            Frames may come from any sheet in the folder.
                            Sprites and animations share ONE pool of names,
                            so an animation cannot reuse a sprite's name.
                            The game's own projectiles are all static - no
                            stock ammo prefab has an Animator - so this is
                            purely a Forge addition.

                            THINGS THAT WILL BITE YOU:
                              - x,y is the rect's TOP-LEFT corner and y counts
                                DOWNWARD, like every image editor. (Unity is
                                bottom-up internally; the mod flips it.)
                              - SCALE: 20 pixels = 1 world unit, and stock art
                                is tiny (the Popper bullet is 7x7 px = 0.35
                                units). A 64x64 PNG is ~9x too big - draw
                                small, or raise pixelsPerUnit to shrink it.
                              - GIF never works at runtime. PNG or JPG only.
                              - Your names live in their own namespace, so
                                they can never collide with the game's ~450
                                sprites. Two of YOUR sheets reusing one name
                                will collide, and the log names it.
                              - Art loads uncompressed; a few small PNGs are
                                free, a hundred big ones cost memory.
                            Anything unreadable is logged under
                            "WeaponForge.Sprites" - a bad name just falls back
                            to the template's art.
  "projectileGlow": false   MY CUSTOM SPRITE LOOKS WASHED OUT / RECOLORED?
                            This is the fix, and nothing is actually tinting
                            it. Some ammo prefabs render through the game's
                            EMISSIVE sprite shader, which is correct for a
                            glowing blob but blows detailed art out toward
                            white. White Derbis does exactly this, so custom
                            art on a lobbed weapon usually wants
                            "projectileGlow": false.
                              false  swap in SpriteUnlitAA - the plain unlit
                                     material the Popper uses, draws art as
                                     painted
                              true   force EmissiveUnlitSprite - the glow -
                                     onto a weapon that didn't have it
                              omit   keep whatever the template used
  "projectileMaterial": "SpriteUnlitAA"
                            Escape hatch: name ANY material asset in the game
                            and it is applied to the shot's sprite renderers.
                            Overrides projectileGlow when both are set. The
                            two that matter are SpriteUnlitAA (as painted)
                            and EmissiveUnlitSprite (glow).
  "projectileSpriteOnly": true
                            "MY SPRITE IS DRAWN ON TOP OF THE OLD ONE" - this
                            is the fix. A projectile prefab is more than one
                            sprite: ammo_Popper carries THREE child particle
                            systems (particle, particle_glow, trail),
                            ammo_Worm two, ammo_Bolt a trail. projectileSprite
                            only replaces the SPRITE RENDERER, so those
                            particles carry on emitting the template's own
                            glow and trail around your art.
                            true switches all the extras off (other sprite
                            renderers, particle systems, trails, lines) and
                            leaves only the sprite you supplied.
                            Off by default, because keeping the template's
                            glow over your own art often looks good - it is
                            only wrong when you were not expecting it.
                            TIP: "Module Weapon White Derbis" has no extra art
                            at all, which is why custom sprites look clean on
                            it without this.

  "trail": { ... }          A STREAK BEHIND THE SHOT. Read the next paragraph
                            first - it explains every option in one go.

                            HOW TRAILS WORK IN THIS GAME. There are no ribbon
                            trails in PUNK. Not one TrailRenderer exists in the
                            whole game, and no prefab turns on Unity's "Trails"
                            module. Every trail is the same thing instead: a
                            small PARTICLE SYSTEM riding along with the shot,
                            dropping little sprite puffs PER UNIT TRAVELLED and
                            leaving them behind in world space. A trail is a
                            line of stamps, not a stretched ribbon - which is
                            exactly why your own sprites can be the puffs.
                            Because it counts distance and not time, the streak
                            keeps the same density at any projectile speed.
                            That is why "perUnit" is the knob you want.

                            Only FOUR ammo prefabs ship a trail (ammo_Popper,
                            ammo_Bolt, Ammo Blades, Ammo Enemy Turret Sniper).
                            For anything else the mod copies the Popper's trail
                            onto your shot and then applies your settings, so
                            these options work on any projectile.

                            Every option is optional. Blank keeps the stock
                            Popper/Bolt value, so this alone already looks like
                            it belongs in the game:
                              "trail": true

                            Shorthands:
                              "trail": true        add a stock trail
                              "trail": false       REMOVE the template's trail
                                                   (nice on the Popper/Bolt
                                                   when your own art should fly
                                                   clean)
                              "trail": "myPuff"    add one made of that sprite

                            Full form and what each key does:

                            "trail": {
                              "enabled":   true,     false removes it
                              "sprite":    "myPuff", puff art - see below
                              "color":     "orange", or #hex, or "rainbow"
                              "rgbSpeed":  0.5,      rainbow only, hue cyc/sec
                              "perUnit":   20,       puffs per world unit
                              "lifetime":  0.025,    seconds each puff lives
                              "size":      0.8,      puff size, world units
                              "sizeEnd":   0,        shrink to this by death
                              "fade":      true,     fade out over its life
                              "speed":     0,        outward drift
                              "gravity":  0,         pull once dropped
                              "perSecond": 0,        puffs/sec - see below
                              "fps":       0,        animated puffs only
                              "sortingOffset": -1,   draw order vs the bullet
                              "template": "ammo_Popper"
                            }

                              perUnit   THE MAIN KNOB. Density of the streak.
                                        Stock 20. Lower = dotted/beaded,
                                        higher = a solid line.
                              lifetime  How LONG the streak is. Stock is a
                                        startlingly short 0.025, which is why
                                        the Popper's trail is a tight smear and
                                        not a comet tail. Try 0.2-0.5 for
                                        something you can actually see trailing
                                        behind. 0 means each puff dies the
                                        instant it spawns - the log warns.
                              size      Thick vs hairline. Stock 0.8. NOTE
                                        projectileScale does NOT scale the
                                        trail (the stock systems are set to
                                        ignore their parent's scale), so size
                                        it here.
                              sizeEnd   Size each puff has reached by the end
                                        of its life. 0 tapers the trail to a
                                        point, which reads as speed. LARGER
                                        than "size" makes puffs swell as they
                                        age instead - expanding smoke, or a
                                        contrail widening behind the shot. Omit
                                        for constant width.
                              fade      Dissolves the streak behind the shot
                                        instead of it stopping dead. Pairs well
                                        with sizeEnd 0. Safe with "color" - the
                                        fade is pure alpha, so it cannot muddy
                                        your tint.
                              speed     Stock 0: puffs sit exactly where they
                                        were dropped, which is what makes a
                                        clean line. Non-zero scatters them
                                        outward for smoke or sparks. 0.2-1
                                        looks like drifting exhaust; large
                                        values stop reading as a trail.
                              gravity   Positive falls, negative rises (rising
                                        smoke). Only worth it with a longer
                                        lifetime, or the puff dies before it
                                        has moved.
                              perSecond Stock 0 and usually leave it there: per
                                        second makes the trail bunch up when
                                        the shot is slow and thin out when it
                                        is fast, the opposite of what a trail
                                        should do. Its one real use is a puff
                                        that keeps emitting while the shot sits
                                        still. If perUnit and perSecond are
                                        BOTH 0 nothing is emitted; the log says
                                        so.
                              sortingOffset
                                        Default -1 = one step behind the
                                        bullet, what the stock trails do. Use 1
                                        to draw the trail OVER the bullet.
                              template  Which prefab's trail to copy when your
                                        shot has none. Defaults to ammo_Popper.
                                        All four stock trails are set up
                                        near-identically, so there is rarely a
                                        reason to change this.

                            THE SPRITE. "sprite" takes a name from your own
                            "sprites" folder OR any sprite in the game, and the
                            custom folder is searched first. Stock puffs worth
                            trying: part_cyrcle_0 ... part_cyrcle_19 are
                            circles from tiny to fat (the stock trail uses
                            part_cyrcle_12 - yes, the game really spells it
                            "cyrcle"), part_engineFIre_0 is a flame,
                            part_impact_Bark_0 a debris chip.

                            AN ANIMATION WORKS HERE. Name an "...Anim" and the
                            whole flipbook is loaded onto the particle, so
                            EVERY PUFF plays the full sequence over its own
                            lifetime and then dies. That is a different look
                            from an animated projectile - the shot stays still
                            and the trail churns. Same naming rules as
                            projectileSprite: a bare sheet name is one frozen
                            frame, "<sheet>Anim" is the flipbook. By default the
                            sequence is stretched across each puff's lifetime so
                            it finishes exactly as the puff dies; set "fps" to
                            pin it to a fixed frame rate instead.
                            A name that isn't found is logged and the stock puff
                            is kept, so a typo never leaves an invisible trail.

                            COLOUR OWNERSHIP. Setting "color" CLAIMS the trail's
                            colour: projectileColor (and its rainbow, if any)
                            will then leave the trail alone instead of painting
                            over it. So a white bullet can trail orange. Leave
                            "color" out and the trail follows the shot's colour
                            like the stock ones do.

                            WORKS WITH projectileSpriteOnly. Deliberately:
                            projectileSpriteOnly silences every particle system
                            on the shot, and THEN the trail is built back up. So
                            "just my sprite, plus a trail I control" is a legal
                            and useful combination, and the order of the keys in
                            your file does not matter.

  WHICH WAY DOES A PROJECTILE FACE?
                            DRAW IT POINTING RIGHT (+X). The game turns a shot
                            with FromToRotation(Vector2.right, direction), so
                            the sprite's RIGHT edge is the nose and its LEFT
                            is the tail. A centred pivot (0.5, 0.5 - what the
                            slicer writes by default) spins it about its
                            middle; move the pivot if you want it to pivot
                            about the tail.

                            The catch differs by weapon type:
                              LOBBED (usePhysics true)  rotated the instant it
                                    spawns, so it always points along its
                                    travel. Nothing to set.
                              STRAIGHT (usePhysics off) spawns with NO
                                    rotation at all. It is only turned if you
                                    set
                                      "rotationData": { "enabled": true,
                                        "orientationAlignment": "WhenShot" }
                                    Without that, your sprite keeps whatever
                                    angle you drew it at no matter which way
                                    you fire - which looks like the art is
                                    flying sideways.
                            (Reminder: "Continuous" is a dead enum value, so a
                            curving shot cannot re-aim itself mid-flight.)

  "projectileColor": "#33ddff"
                            Recolor the projectile or beam. Accepts a
                            hex value ("#33ddff"), an HTML color name
                            ("cyan"), a game color ("ColorBlue"), or
                            "rainbow" for an animated RGB cycle.
                            Projectiles: tints sprites/trails/particles.
                            Hitscan: tints the beam sprite, light, and
                            impact particle.
                            It MULTIPLIES, so it fights your own art - leave
                            it out (or use white) when you have set
                            projectileSprite. Two useful extremes:
                              "#ffffff00"  makes the shot completely
                                           INVISIBLE (alpha 0). Genuinely
                                           useful for an unseen carrier
                                           shot, a pure-explosion weapon, or
                                           a turret disc you don't want to
                                           see.
                              a dark value dims the shot rather than
                                           darkening it.
  "rainbowSpeed": 0.5       Rainbow only: hue cycles per second (0.5 =
                            a full rainbow every 2 seconds). Default 0.5.
  "projectileScale": 1.5    Size multiplier. Projectiles: bigger shot
                            AND a matching larger hit radius. Hitscan:
                            beam thickness. Minions are only recolored,
                            never scaled (scaling breaks their AI).
  "burnTickRate": 0.1       BURN options (need a burn source - burn from
  "burnColor": "rainbow"    this weapon, or an AddBurnEffect). While the
  "burnRgbSpeed": 0.5       weapon is equipped:
  "burnColorTerrain": true    burnTickRate     ticks/sec ADDED to how fast
                                               burn ticks on ENEMIES
                                               (stacks with other burn
                                               weapons/modules; capped).
                              burnColor        recolor ENEMY burn flames -
                                               a color name / #hex, or
                                               "rainbow" for RGB cycling.
                              burnRgbSpeed     rainbow only: hue cycles/sec.
                              burnColorTerrain also recolor burning terrain
                                               (default false).
                            Your OWN burn is never sped up or recolored.
                            These cooperate with the Module Forge mod if
                            it's installed (no conflict); they also work
                            with Weapon Forge alone.

CUSTOM SOUNDS
-------------
The sound fields take EITHER a sound id the game already has, OR the
name of an audio file you supply. Drop a file in a "sounds" folder
next to the DLL and use its file name without the extension:

  sounds/mylaser.wav   ->   "shootSfx": "mylaser"

The seven slots, and when each one plays:

  shootSfx           once per volley, at the barrel. Works in EVERY
                     slot - primary, secondary, gadget, and
                     sub-emitter stages.
  reloadSfx          when the cooldown finishes and the weapon is
                     ready again.
  startSfx           one-shot as the trigger goes down.
  continousShootSfx  LOOPS while the trigger is held (beams,
                     flamethrowers). Game's own typo - one 'u'.
                     Primary/secondary only; a gadget never starts it.
  releaseSfx         one-shot when that loop stops.
  warmupSfx          LOOPS during warmupTime.
  explosion.sfx      the boom (inside the "explosion" block).

FILE TYPES
  .wav   BEST. Decoded directly by the mod - always works, and the
         clip is ready instantly. Any bit depth (8/16/24/32-bit PCM
         or 32-bit float), mono or stereo.
  .ogg   Works. Decoded by the engine a frame after startup.
  .mp3   Usually works, but it leans on the platform's decoder. If a
         file stays silent, convert it to .wav.
  .aiff  Same route as ogg.
The GAME cannot load audio files at all - it ships pre-baked clips -
so this is the mod decoding your file and handing the engine a real
AudioClip.

IT BECOMES A REAL GAME SOUND. The clip is registered into the game's
own audio database, so 3D positioning, the in-game SFX volume slider,
the audio mixer, voice pooling and repeat throttling all apply to it
exactly as they do to a stock sound. Anything you don't specify is
COPIED FROM THE SOUND YOU REPLACED, so a custom beam loop loops and a
custom gunshot doesn't.

  continousShootSfx and warmupSfx are FORCED to loop no matter what
  they replaced. The game starts those, keeps the handle, and stops
  them by handle later - a one-shot there would play once and never
  restart. Give them a seamless loop; they get cut off when you let
  go of the trigger, which is what releaseSfx is for.

TOO LOUD? Very likely - exported audio is usually much hotter than
the game's. Put a .json beside the audio file with the SAME NAME:

  mylaser.wav
  mylaser.json   ->  { "volume": 0.6 }

  volume          0 to 1. The first thing to reach for.
  looping         true/false (set for you on the two held slots).
  is3d            true = positioned in the world (default),
                  false = flat.
  priority        0-256, lower wins when sounds compete.
  repeatMinDelay  seconds before the same sound may retrigger. Raise
                  it if a fast weapon sounds like a buzzsaw.
  cancelPrevious  true = a new play stops the previous one.
  variants        several files picked at RANDOM per shot, which is
                  how the game's own gunshots avoid sounding
                  mechanical:
                    { "variants": ["shot1.wav", "shot2.wav"] }
                  Files listed here don't also become sounds of their
                  own.

NO PITCH CONTROL exists - the game never touches AudioSource.pitch,
so bake pitch variation into the files (that is what variants are
for).

A misspelled name is reported in the log with a list of the sounds
that DID load, and the slot goes silent rather than falling back - so
check the log if a weapon loses its sound. For a STOCK sound the
value must be the audio GUID, not the readable path: the lookup
compares GUIDs only, so "Weapons/Bolt/Shoot" is silence. The builder
page has pickers for the stock ones.

Projectile/beam color is NOT tied to the damage resource in this
game - changing damageType recolors damage numbers/UI only, not the
shot. Use "projectileColor" to actually recolor the shot. Weapon
Forge clones the visual per-weapon, so recoloring never affects the
stock weapon you cloned from.

 6. TYPE-SPECIFIC FIELDS
----------------------------------------------------------------

PROJECTILE templates also accept:

  "projectileSpeed": 30
  "projectileSpeedVariance": 2
  "projectileRadius": 0.2      Hit size of the projectile.
  "usePhysics": false
  "collidesWithSlime": true
  "projectilePrefab": "..."    Asset name of ANOTHER weapon's
                               projectile - steal its look!
  "rangeData": { "enabled": true, "range": 10, "variance": 1,
                 "slowDown": false, "destroyWhenReached": true,
                 "spawnExplosion": false, "fireSub": false,
                 "destroyEffect": "EndParticle Ammo Toroid" }
  "lifetimeData": { "enabled": true, "time": 3,
                    "spawnExplosion": true,
                    "fireSub": false, "discharge": false,
                    "spawnOnTimeDown": "Explosion Ammo Fireball" }
      "timeVariance" exists in lifetimeData but DOES NOTHING - nothing
      reads it. For a randomised despawn use rangeData range+variance.

  END-OF-LIFE / IMPACT EFFECTS - three separate prefab slots, all
  resolved by asset NAME, all purely cosmetic (no damage). Stick to
  names stock weapons already use, or the lookup finds nothing and the
  field is skipped without a warning:
      "impactBehaviour": { "destroyEffect": "ImpactParticle Ammo Popper" }
            the HIT effect. 42 of the 80 stock projectile weapons set
            it, and it is the biggest single reason a forged weapon can
            feel flat - without it, shots just vanish. Good values:
            ImpactParticle Ammo Popper / Fly / Flame / Toroid /
            FlyZapper / Derbis / Worm / Cross / CrossAlpha, or the
            beefier Explosion Ammo Marbles / Fireball / SoldierTech /
            Rocket Soldier / Fish, EndParticle Ammo ElectronRocket,
            DeathParticle Ammo Disc.
      "rangeData": { "destroyEffect": "..." }
            for running out of RANGE instead of hitting something.
            Needs destroyWhenReached. Set both this and the impact one
            if you want the shot to look right either way. Good values:
            EndParticle Ammo FlyZapper / ElectronRocket / Toroid,
            ImpactParticle Ammo Toroid, Explosion Ammo Fireball /
            SoldierTech, DeathParticle Ammo Disc Disappear,
            DeathParticle Weapon Worm.
      "lifetimeData": { "spawnOnTimeDown": "..." }
            for the lifetime TIMER running out. Independent of
            spawnExplosion (that one deals the damage, this is the
            look).
      Also in impactBehaviour: "destroyVelocityThreshold" - LOBBED
      shots only, does nothing on a normal projectile.
  "homingData": { "enabled": true,
                  "targetMode": "AutoSeekWhenShot",
                  "acceleration": 20, "torque": 200,
                  "maxSpeed": 15, "maxAngularVelocity": 400,
                  "turbulenceTorque": 0,
                  "turbulenceFrequency": 0 }
        targetMode options: FromLockOnly, AutoSeekWhenShot,
                            AutoSeekWhenNeeded
  "piercingData": { "enabled": true, "damageRepeatDelay": 0.2,
                    "knockBackRepeatDelay": 0.2 }
      Vanilla piercing is UNLIMITED (passes through every enemy). To cap
      it, use these TOP-LEVEL keys (not inside "weapon"):
        "pierceLimit": 2          enemies it pierces THROUGH before it
                                  vanishes on the next contact (that last
                                  enemy still takes the hit). Auto-enables
                                  piercing. Projectile weapons only.
        "pierceDamageFalloff": 0.2  damage lost per enemy pierced (0.2 =
                                  -20% to each successive enemy).
        "pierceExplodeOnLimit": true  explode when it hits the cap.

  PHASING (no-clip through terrain) - TOP-LEVEL keys:
    "phasing": true           the projectile/beam passes THROUGH terrain
                              but still hits enemies. Works on projectile
                              and hitscan/laser weapons.
    "phaseInfiniteRange": true  hitscan/laser only - the beam no longer
                              stops on walls so it reaches very far. (Or
                              set "weapon": { "range": N } to your own
                              value instead.)

  WAVE MOTION (make projectiles fly a curve instead of a straight line):
  There are TWO flavors -
   (1) CLEAN SINE "wave beam" (Super Metroid style) - TOP-LEVEL keys:
    "wave": true              projectile weaves a crisp, repeating S.
                              Projectile weapons only (NOT usePhysics/lobbed).
                              Collisions follow the visible curve. See
                              ExampleWaveBeam.json. NOTE: wave and wobble are
                              mutually exclusive - if both are on, wave wins
                              and the wobble is turned off automatically.
    "waveAngle": 30           how far the heading swings, in degrees (the
                              "width"/sharpness of the S).
    "waveFrequency": 2        wiggles per second (with projectileSpeed this
                              sets the wavelength).
    "waveMode":               how several projectiles wave together:
       "single" (default) each shot's S starts centered on its own timer.
       "synced"  rapid fire forms ONE continuous ribbon (shared clock).
       "helix"   alternate projectiles start 180 out of phase - the woven
                 "double helix" look (needs 2+ projectiles).
   (2) ORGANIC WOBBLE (a random Perlin wander, NOT a clean S) - this is the
       game's own built-in "movementNoiseData" (below). Two easy ways:
    "wobble": true            turns it on with sensible defaults.
    "wobbleAngle": 30         max wander in degrees.
    "wobbleFrequency": 3      how fast it wanders.
       ...or set "weapon": { "movementNoiseData": {...} } directly (below).

  HOMING (bullets that curve onto enemies) - TOP-LEVEL "homing" block.

  WHY THIS EXISTS. The game HAS homing - "homingData" - but it only works on
  LOBBED / PHYSICS shots. ProjectileWeapon hands homingData to the projectile
  ONLY inside its usePhysics branch, so a fast straight bullet like the
  Popper's can never home with stock data no matter what you write. Stock
  homing is also a RIGIDBODY model (torque, angular velocity, thrust) that a
  plain bullet has no parts for.

  So "homing" is homing for the PLAIN projectile. It steers by rotating the
  shot's velocity, and there is a happy accident in how the game is built
  that makes this the right way round: a plain projectile's collision sweep
  is rebuilt FROM its velocity every frame -
      Physics2D.CircleCast(position, Radius, Velocity, ...)
  - so bending the velocity bends THE HITBOX TOO, automatically. There is no
  second raycast to keep in sync, which is exactly what makes bending a
  hitscan beam hard by comparison.

      "homing": true            on, with defaults
      "homing": {
        "enabled": true,
        "turnRate": 240,
        "range": 20,
        "cone": 45,
        "delay": 0.15,
        "maxTurn": 120,
        "retarget": true,
        "predict": false,
        "faceTravel": true
      }

    turnRate    degrees per second the heading may swing. THE dial. What you
                actually SEE is the turn RADIUS, which is
                speed / turnRate (in radians) - so the same turnRate that
                whips a slow shot around barely bends a fast one.
                At projectileSpeed 30: turnRate 180 gives a ~9.5-unit turn
                radius (a nice visible arc), 360 gives ~4.8 (a hard chase),
                90 gives ~19 (almost straight). The mod LOGS the computed
                radius for your actual numbers and warns when it is too wide
                to see, so check the log if "homing does nothing".
    range       how far the shot looks for something to chase. Only things it
                could actually hit count, and never terrain.
    cone        only acquire a target within this many degrees of where the
                shot is already going, so bullets don't turn round and fly
                backwards. Default 90. 180 = anything, including behind.
                Narrow it (30-45) for shots that only lock onto roughly what
                you aimed at, which keeps a stream sweeping smoothly instead
                of snapping sideways.
    delay       seconds of dead-straight flight before homing starts. Small
                values read really well on a beam-like stream - it leaves the
                muzzle straight and bends further out. Try 0.1-0.2.
    maxTurn     total degrees this shot may EVER turn (0 = no limit). A
                budget (say 90) stops a missed shot from circling forever and
                coming back at you: it commits to one graceful curve, then
                flies straight.
    retarget    find a new target if the current one dies (default true).
                With a high fire rate and enemies dying constantly this keeps
                the stream latched onto whatever is still alive.
    predict     aim where the target is GOING, using the game's own aim-assist
                velocity. Better against movers; on a slow shot against a fast
                mover it can overshoot and weave.
    faceTravel  rotate the sprite to match the new heading each frame
                (default true). Needed for art with a nose, and essential for
                a segment stream to read as one continuous curve. Turn it off
                for a round blob, or to let a rotationData spin survive.

  Projectile weapons only, and NOT usePhysics - a lobbed shot has the game's
  own homing instead, and the mod says so in the log with the homingData to
  use. Like wave, homing turns movementNoiseData OFF, because the game's noise
  branch recomputes the heading after ours and would undo every turn.

  MAKING IT LOOK LIKE A BEAM. Spacing between shots is
  projectileSpeed / fireRate, and the stream looks continuous when your sprite
  is at least that long. The game runs at 20 PIXELS PER WORLD UNIT, so:
      speed 30, fireRate 20  -> 1.5 units apart -> needs a ~30 px sprite
      speed 24, fireRate 30  -> 0.8 units apart -> needs a ~16 px sprite
  Shorter and you get a dotted line, which with the right art is its own good
  look. Also worth setting: piercingData.enabled true so the stream doesn't
  stop dead on the first enemy (a real beam doesn't), a small "cost" since you
  are firing many times a second, and "repeatMinDelay" in your custom shoot
  sound's .json so it doesn't machine-gun into noise.

  BULLET DEFLECTOR - TOP-LEVEL "deflect" block.

  The shot clears enemy bullets out of the air as it travels - destroying
  them, or TURNING THEM AROUND and sending them back. This is the first
  DEFENSIVE weapon in the mod, and a slow disc swept across incoming fire
  plays completely differently from anything else here.

  WHY A HAND-ROLLED VERSION WOULD NOT WORK: PUNK projectiles resolve
  their own collisions with a CircleCast, so their Collider2D is DISABLED
  on the prefab. Enemy bullets are invisible to Physics2D.OverlapCircle -
  a query finds nothing no matter how big the radius. The mod keeps its
  own register of live enemy shots instead, switched on only when a
  weapon needs it.

      "deflect": true           on, destroys fire within 2 units
      "deflect": {
        "enabled": true,
        "mode": "reflect",
        "aim": "nearest",
        "radius": 3,
        "maxTotal": 0,
        "damage": 1.5,
        "speed": 1.3,
        "interval": 0.05,
        "aimRange": 25
      }

    mode      "destroy" (default) makes incoming fire vanish - reliable
              and readable, good for carving a safe lane through a bullet
              wall. "reflect" re-factions the bullet so it becomes YOURS:
              it damages enemies, cannot hit you, and kills with it are
              credited to you. More satisfying, and it scales with how
              much the enemy is shooting rather than with your damage.
    aim       reflect only. "back" (default) is honest physics and often
              returns it to whoever fired it. "nearest" re-aims at the
              closest valid target instead, which connects far more often
              - same target-finder as "homing", so it never picks terrain
              or your own side.
    radius    how far from the shot fire is caught. 2 is a comfortable
              bubble; 5+ turns one shot into a moving safe zone, which is
              powerful - pair it with a slow fire rate or a maxTotal.
    maxTotal  how many shots ONE projectile may deal with over its life.
              0 = unlimited. A small number (2-3) makes each deflector
              shot a precious aimed thing rather than a blanket shield.
    damage    reflect only: multiplier on the returned bullet's damage.
    speed     reflect only: multiplier on its speed. Above 1 helps it
              reach the enemy before they move.
    interval  seconds between sweeps (default 0.05). It is a distance
              test over every live enemy bullet, and 20x/sec looks
              identical to every frame at a fraction of the cost.
    aimRange  how far a reflected bullet looks for a target (default 25).

  Pairs naturally with a slow, long-lived, low-damage shot. Projectile
  weapons only, not usePhysics. Preset: "Deflector".

  GROWING / SHRINKING SHOT - TOP-LEVEL "grow" block.

  A pinprick that arrives as a wrecking ball, or a fat slug that tapers
  away to nothing.

  THE HITBOX GROWS WITH THE ART, AUTOMATICALLY. The game rebuilds a
  projectile's collision circle from its Radius every single frame, and
  that value is writable - so the thing you SEE and the thing that HITS
  are driven by the same number and cannot drift apart.

  Sizes are MULTIPLIERS of the shot's normal size, so 1 = unchanged and
  this composes with projectileScale / projectileRadius instead of
  fighting them. Set "from" larger than "to" and it shrinks instead.

      "grow": true              on, with defaults (0.4 -> 3 over range)
      "grow": {
        "enabled": true,
        "from": 0.25,
        "to": 3.5,
        "over": "distance",
        "span": 16,
        "damageAtFull": 2.5,
        "curve": 1.6,
        "hitbox": true,
        "clamp": true
      }

    from / to    size at launch and at full growth, as multipliers.
                 0.4 -> 3 is a dramatic but readable wrecking ball.
                 Remember the hitbox comes with it, so a big "to" is a
                 real accuracy buff, not just a look.
    over         "distance" (default) grows with how far it has flown -
                 consistent regardless of projectile speed. "time" grows
                 with seconds alive instead, so a slow shot grows over a
                 short distance.
    span         how far (units) or how long (seconds) to reach full
                 size. LEAVE IT OUT and it borrows the weapon's own
                 rangeData.range - or lifetimeData.time in time mode - so
                 the shot peaks exactly as it expires, which is almost
                 always what you want. With neither set it falls back to
                 10 units / 2 seconds, and the log says which it used.
    damageAtFull damage multiplier once fully grown, ramping along the
                 way. 1 (default) = damage never changes. 2 rewards
                 letting the shot travel - the natural partner to a
                 growing bullet.
    curve        shape of the ramp. 1 = steady. Above 1 (try 2-3) stays
                 small then swells at the last moment, reading as a
                 charge-up. Below 1 (try 0.5) swells fast then eases.
    hitbox       default true. False makes it purely cosmetic - looks
                 huge, hits normally.
    clamp        default true. False lets it keep growing past "to" for
                 as long as the shot lives.

  One thing that deliberately does NOT scale: a "trail". The game's
  particle trails ignore their parent's scale, so the puffs stay their
  own size while the shot balloons. Usually looks right - set the
  trail's own "size" if you want it to match.

  Projectile weapons only, not usePhysics. Preset: "Snowball".

  BOOMERANG (flies out, turns around, comes back) - TOP-LEVEL "boomerang".

  THE GAME ALREADY DOES THE OUTBOUND HALF. A weapon whose rangeData has
  "slowDown" on DECELERATES as it approaches its range - and Module
  Weapon White DiscGun ships exactly that, range 8 with slowDown on. By
  the time the disc reaches the far end its speed is already ZERO. That
  zero is a free, natural pivot: no snap turn, nothing to tune. So this
  block only supplies the trip home, and the DiscGun is the obvious base
  (it already flies out, slows, stops, and it spins).

  Turning it on will ENABLE rangeData if you haven't (there would be
  nothing to turn at), force slowDown on, and switch OFF
  destroyWhenReached - which would otherwise kill the shot at the exact
  moment it should be turning round. All three are logged.

      "boomerang": true          on, with defaults
      "boomerang": {
        "enabled": true,
        "returnPath": "home",
        "returnOn": "range",
        "returnSpeed": 1.2,
        "returnDamage": 1.5,
        "onCatch": "vanish",
        "refund": 0.5,
        "passes": 2,
        "pierce": true,
        "rehit": true,
        "turnRate": 540,
        "catchRadius": 1.2,
        "maxLife": 12
      }

    returnPath   "home" (default) curves back to wherever your ship is
                 NOW, so it always reaches you even if you moved.
                 "retrace" flies back along the path it came out on,
                 using breadcrumbs dropped 20x a second - so if the throw
                 curved (wave, homing) the return curves too. Faithful,
                 and good for hitting the same row twice, but if you have
                 moved it returns to where you WERE and expires there.
    returnOn     "range" (default) turns only at the far end.
                 "hit" also turns it the moment it strikes TERRAIN, which
                 feels reactive in tight spaces. Enemies never turn it -
                 it pierces them.
    returnSpeed  multiplier on the launch speed for the trip home. 1 =
                 same as it went out. Above 1 snaps back at you, which
                 reads well because the outbound leg ends slow.
    returnDamage damage multiplier applied ONCE as the return begins.
                 1.5 rewards letting the arc finish instead of firing
                 into a wall.
    onCatch      "vanish" (default), "refund" (pays back a share of the
                 weapon's cost into the tank it was fired from - needs
                 the weapon to have a cost), or "loop" (throws itself out
                 again, "passes" times).
    pierce       DEFAULT TRUE, and it matters: the DiscGun has piercing
                 OFF, so out of the box it stops dead on the first thing
                 it touches - and a boomerang that never gets past an
                 enemy never comes back. True switches piercing on.
    rehit        default true: a lined-up throw hits everything twice.
                 Under the hood this is the per-target damage cooldown at
                 0.3s - long enough that passing THROUGH an enemy still
                 counts once, short enough that the return lands.
    turnRate     how sharply it curves home, deg/sec (default 540). Too
                 low and it circles you instead of being caught.
    catchRadius  how close counts as caught (default 1.2).
    maxLife      safety net in seconds (default 12). Needed because
                 destroyWhenReached is off for these, so a shot whose
                 return stalled would otherwise live forever.

  Projectile weapons only, not usePhysics. See ExampleBoomerang.json.

  RICOCHET (bullets that bounce off things) - TOP-LEVEL "ricochet" block.

  WHAT IS THE GAME'S AND WHAT IS OURS. The bouncing itself is the game's
  (projectileBounceData), and so is choosing which surfaces bounce. Usefully,
  the damage call happens BEFORE the bounce, so a shot that ricochets off an
  enemy HAS ALREADY HURT IT. Only two stock weapons use any of it
  (CrossRedElectron Bouncer, SoldierTech - both terrain-only).

  What the game has NO concept of is a bounce COUNT. Nothing anywhere tracks
  reflections, so a stock bouncer bounces FOREVER until range or lifetime
  kills it. The limit, the falloff, the scatter and the seeking are what this
  block adds.

      "ricochet": true          on, terrain-only, 3 bounces
      "ricochet": {
        "enabled": true,
        "targets": "both",
        "bounces": 5,
        "seek": true,
        "seekRange": 20,
        "seekCone": 180,
        "scatter": 8,
        "speedMultiplier": 0.85,
        "damageMultiplier": 0.8,
        "pierceWins": false
      }

    targets     what it bounces off:
                  "terrain" (default)  walls only - the classic bouncer
                  "enemies"            skips between enemies like a stone
                                       across water
                  "both"               walls and enemies
                  "none"               parks the feature without deleting
                                       your settings
                Under the hood this is the game's bounce layer mask, resolved
                by layer NAME (terrain = "Ground", enemies = "Entities") so a
                layer reshuffle cannot silently retarget it.
    bounces     how many bounces before the shot is done. A NUMBER, or
                "infinite" (also accepts "unlimited" / -1). Default 3.
                CAREFUL WITH INFINITE - that is the stock behaviour, and with
                no rangeData or lifetimeData the shots never die and pile up.
                The mod warns in the log if you set infinite with no way to
                expire. Give it "lifetimeData": { "enabled": true,
                "time": 3 }.
    seek        false (default) = an honest mirror bounce off the surface,
                which goes wherever the geometry sends it - often nowhere.
                true = each bounce is redirected at the nearest valid enemy,
                which is what makes a ricochet reliably "hit something else".
                Uses the same target-finding as "homing", so it agrees on what
                counts as a target and never picks terrain or your own side.
    seekRange   seek only: how far to look from the bounce point.
    seekCone    seek only: how far off the TRUE reflected heading the redirect
                may pull, in degrees. 180 (default) = anywhere, including
                straight back. Lower it (60-90) to keep the bounce looking
                physically plausible while still cheating.
    scatter     degrees of random angle added to each bounce. Besides feeling
                chaotic rather than geometric, this is the practical ESCAPE
                FROM A SHOT TRAPPED BETWEEN TWO PARALLEL WALLS, which a
                perfect mirror would ping between until it expires. Try 5-15.
    speedMultiplier
                fraction of speed kept per bounce. 1 = arcade (default, and
                what the stock bouncers do). 0.8 makes a long chain visibly
                wind down. Note a slowing shot also curves TIGHTER if you
                have "homing" on, since turn radius scales with speed - which
                happens to look right.
    damageMultiplier
                fraction of damage kept per bounce. 1 = no falloff (default).
                A balance lever if an infinite bouncer in a tight corridor
                turns out absurd: 0.7 makes the fourth hit worth about a third
                of the first.
    pierceWins  ONLY matters if piercingData is also on. The game checks
                piercing BEFORE bouncing and returns early, so a pierced enemy
                is never bounced off - the two cannot both apply to one hit.
                Terrain is exempt from that early-out, so walls bounce either
                way.
                  false (default)  you asked for ricochet, so piercing is
                                   switched OFF and the log says why.
                  true             piercing is kept, shots pass through
                                   enemies, and only terrain ricochets.

  WHEN THE BOUNCES RUN OUT the shot runs the weapon's own impactBehaviour on
  that final hit and is then destroyed - so if you set spawnExplosion or a
  subEmitter, the last bounce goes off with a bang; with nothing set it simply
  vanishes. Nothing to configure; it reuses the impact machinery you already
  have.

  Plain projectiles only. Lobbed / usePhysics shots have NO bounce code at all
  in the game, so ricochet is refused on them with a log line.

  Small honest caveat: the game also calls its Reflect() for the impact
  "safety distance" bounce (a shot that hits something right at the muzzle is
  bounced instead of exploding, so weapons do not blow up in your face). Those
  consume a bounce too, which is why a point-blank shot can look like it lost
  one early.

  "projectileBounceData": { "enabled": true }
  "movementNoiseData": { "enabled": true, "angle": 15,
                         "frequency": 6 }
      Organic Perlin wobble (see "wobble" above for the easy alias). This is
      a wandering path, not a clean S - use "wave" for a clean wave beam.
  "impactBehaviour": { "enabled": true, "spawnExplosion": true,
                       "fireSub": false, "discharge": false,
                       "safetyDistance": 1 }
  "electricityData": { "enabled": true, "isSource": true,
                       "chainLength": 6, "conductivity": 20,
                       "minConductivity": 0,
                       "emittedSystem": "Player",
                       "conductedSystem": "Player",
                       "showPreviewBeam": true,
                       "showBeamParticles": true,
                       "damageRadius": 0.75,
                       "damageRepeatDelay": 0.1,
                       "layerMask": "Entities",
                       "limitedCharge": true, "maxCharge": 5,
                       "damage": { "amount": 3,
                                   "damageType": "Resource White" } }
      "layerMask" - which layers the conductor may link into and damage.
            Same trap as discharge.layerMask: a typo silently means
            "conducts to nothing", with no warning anywhere.
      "limitedCharge" + "maxCharge" - makes the shot's electricity a
            finite battery instead of an endless source: it starts full
            at maxCharge and drains as it conducts, so the arc
            eventually dies. Six stock weapons use it (Electron Circuit
            = maxCharge 5). Always set BOTH - limitedCharge on its own
            with maxCharge 0 is a conductor that is dead on arrival.

HITSCAN templates also accept:

  "range": 12                Beam length.
  "rayWidth": 0.3            Beam thickness.
  "damageRepeatDelay": 0.25  Seconds between damage ticks while
                             the beam stays on a target.

PHYSICS templates also accept:

  "projectileSpeed": 10
  "projectileSpeedVariance": 1
  "projectilePrefab": "..."  (a physics object prefab name)

MINION SPAWNER templates also accept:

  "minionPrefab": "..."      Which unit gets spawned.
  "projectileSpeed": 5       Launch speed of the minion.
  "minionFacesShootDirection": true

----------------------------------------------------------------
 6a. NORMAL PROJECTILES (the plain bullet) - WHAT APPLIES
----------------------------------------------------------------

The default and most flexible type: a Projectile weapon with usePhysics
OFF. The shot flies dead straight at a fixed speed, swept forward by a
circle-cast every physics step. Stock reference points:

  White Popper   fireRate 7,   damage 1, speed 100, radius 0.22, range 15
  White Bolt     fireRate 0.7, damage 4, speed 200, radius 0.24, range 20,
                 knockbackForce 270
  White Shotgun  fireRate 1.3, damage 1 x projectileCount 10, spread 20,
                 speed 100, range 9

EVERYTHING in section 4 and 5 applies, plus every Forge extra (wave,
orbit, phasing, pierce cap, turret, sub-emitters).

*** SPREAD vs ANGLEVARIANCE - the one that catches everybody ***

  "spread" is the total width of an evenly-spaced FAN, and it is
  COMPLETELY IGNORED when projectileCount is 1. The stock Popper ships
  spread 7 and the Bolt ships 10, and on both of them that number does
  absolutely nothing - until a +projectile module lands, at which point
  the weapon suddenly fans out.

  "angleVariance" is a random wobble applied to each shot on its own.
  THAT is the inaccuracy knob for a single-shot weapon.

  Shotgun -> spread.  Rattly machine gun -> angleVariance.

  The fan itself: with count > 1 the shots start at
  (-spread / 2 + angleOffset) and step by spread / (count - 1), so the
  first and last shot land exactly on the edges. One special case:
  "spread": 360 steps by spread / count instead, which is what stops a
  full circle from putting two shots at the same angle.

  "projectileCount" is a FLOAT and the loop is "while i < count", so
  2.5 fires THREE shots (and spaces them as if there were 2.5). Use
  whole numbers unless you want that.

DOES NOTHING on a normal projectile - do not waste time on these:

  "homingData"                            missiles need usePhysics; a
                                          straight shot has no homing
                                          code at all (see 6c)
  "physicsProjectilePrefab"               only read when usePhysics is on
  "lifetimeData.timeVariance"             never read by ANY code path.
                                          Looks like the randomiser
                                          rangeData.variance is, but the
                                          expiry check uses the raw
                                          .time. Use rangeData instead.
  "rotationData.orientationAlignment":
      "Continuous"                        dead enum value - the game
                                          tests only for "WhenShot", so
                                          a curving shot will not keep
                                          re-aiming. For a spinning shot
                                          pick art that spins (Blades,
                                          Disc).
  "impactBehaviour.
      destroyVelocityThreshold"           lobbed shots only
  "cellConvertData"                       hitscan beams only (see 6d)
  "maxRotationSpeedWhileShooting"         reads like an aim-speed clamp
                                          while firing, and it IS real -
                                          but only the enemy AI aimer
                                          uses it. The player ship aims
                                          through a different component
                                          that never looks at it, so it
                                          does nothing on anything you
                                          can build. Not offered in the
                                          builder for that reason.
  "rayWidth" / "layerMask" / "visual"     hitscan fields
  "minionPrefab" and friends              minion spawners only

EASY TO MISS: a projectile's per-target damage cooldown is
"piercingData.damageRepeatDelay". The top-level "damageRepeatDelay" is
the HITSCAN beam's tick rate and exists only on that type - setting it
on a projectile weapon is silently discarded.

----------------------------------------------------------------
 6b. LOBBED WEAPONS (usePhysics) - WHAT APPLIES
----------------------------------------------------------------

*** rangeData DOES NOTHING ON A LOB - the whole block ***

  A lobbed shot is a PhysicsProjectile, a different class from a straight
  shot, and it ignores rangeData completely. It reads the values and
  computes a time-to-range on launch, then never looks at that number
  again - so "range", "variance", "slowDown", "destroyWhenReached",
  "spawnExplosion" and "fireSub" are ALL inert here. (A straight shot uses
  the same number for its slow-down and its range-expiry; the physics one
  simply has no equivalent code.)

  So a lobbed shot only ever ends two ways, and only these fire a sub:
     lifetimeData.fireSub       when its timer runs out
     impactBehaviour.fireSub    when it hits something
  Want it to burst after N seconds in the air? That is
     "lifetimeData": { "enabled": true, "time": 2, "fireSub": true }
  not rangeData.
  Impact still respects impactBehaviour.safetyDistance: a shot that hits
  something closer than that does not fire its sub.

Set "usePhysics": true (inside "weapon") and the weapon throws a physics
object that arcs, tumbles and bounces off the world.

  "physicsProjectilePrefab": "..."   THE ammo for a lobbed weapon. A lob
        weapon IGNORES projectilePrefab completely and uses this instead,
        so this is the field to change to throw different debris.

  "velocityInfluenceData": { "multiplyer": 1, "limit": 8,
                             "influenceMode": "Projected",
                             "allowSlowDown": false }
        Feeds YOUR ship's movement into the shot - fly forward and the
        lob goes further. Very characterful on grenades.
          multiplyer     how much of your velocity is added (1 = all,
                         0 = none). NOTE the game's spelling.
          limit          caps the added speed.
          influenceMode  "AnyDirection" adds your movement as-is, so
                         strafing curves the throw; "Projected" keeps
                         only the part along your aim, so it just goes
                         further or shorter.
          allowSlowDown  true lets backing away SUBTRACT speed; false
                         only ever speeds the shot up.

WHAT WORKS on a lobbed shot:
  damage & burn, explosion, discharge, impactBehaviour, rangeData,
  lifetimeData, homingData, pushForce, subEmitter, collidesWithSlime,
  electricityData, velocityInfluenceData.

WHAT DOES NOTHING on a lobbed shot (it never spawns the straight-flying
projectile these belong to):
  piercingData / pierceLimit, projectileBounceData (the physics object
  already bounces), movementNoiseData, rotationData, projectileRadius,
  and the custom "wave", "phasing" and "turret" options.

----------------------------------------------------------------
 6c. MISSILES (homingData) - WHAT APPLIES
----------------------------------------------------------------

*** HOMING ONLY WORKS ON A PHYSICS SHOT. ***
Set "usePhysics": true or homingData does NOTHING - the straight-flying
projectile has no homing code at all. Every one of the game's 13 homing
weapons is a physics shot, player and enemy alike.

Player missiles:  White Dart, Purple Rocket, Caps Rocket, Electron Rocket
Enemy missiles:   Weapon Enemy DroneMissile, Weapon OfficerPurple Missile,
                  Weapon FloaterOfficerCaps Rocket, Weapon Purple Surge,
                  Weapon Rocket Fire / JockRocket / Rookie / Soldier /
                  TurretSeeker, Weapon Rocket CrossRedSmallElectron

HOW A MISSILE FLIES: it is steered by TORQUE - it rotates toward the
target and thrusts along its own nose. It never strafes sideways, so a
low torque makes it swing wide and overshoot.

  "homingData": {
    "enabled": true,
    "targetMode": "AutoSeekWhenShot",
    "torque": 5, "maxAngularVelocity": 1000,
    "acceleration": 70, "maxSpeed": 100,
    "turbulenceTorque": 15, "turbulenceFrequency": 4,
    "turbulenceDistanceCurve": [[0,0],[2.1,0],[10,1]]
  }
  (those are the stock rocket values)

  targetMode
     "FromLockOnly"        only chases what your AIM ASSIST has locked, so
                           it needs aimAssistData enabled - with no lock it
                           just flies straight
     "AutoSeekWhenShot"    grabs the nearest target as it spawns
     "AutoSeekWhenNeeded"  keeps looking mid-flight, so it can re-acquire
  torque               TURN STRENGTH - the main missile knob.
  maxAngularVelocity   spin limiter: no more turn force is added once it is
                       already rotating this fast.
  acceleration         forward thrust, applied while under maxSpeed.
  maxSpeed             thrust cuts out at this speed.
  turbulenceTorque     drunken wobble on top of the steering (0 = clean).
  turbulenceFrequency  how fast that wobble changes.
  turbulenceDistanceCurve   how the wobble scales with DISTANCE TO TARGET,
                       written [[distance, amount], ...]. This is the
                       secret of the rocket feel: the stock curve is
                       [[0,0],[2.1,0],[10,1]] - full wobble at range 10,
                       fading to ZERO within about 2 units, so rockets
                       flail on approach then commit at the last moment.
                       [[0,1]] = wobble everywhere, [[0,0]] = never.

Because a missile is a physics shot, section 6b applies to it too: it can
use explosion, burn, discharge, subEmitter, rangeData/lifetimeData and
velocityInfluenceData, but NOT piercing, bounce, movementNoise, rotation,
wave, phasing or turret.

----------------------------------------------------------------
 6d. HITSCAN / LASER BEAMS - WHAT APPLIES
----------------------------------------------------------------

A hitscan weapon has NO projectile. It circle-casts a line every frame
and damages whatever it touches, so most projectile options do nothing.

  "range": 30            beam length. Caps Laser ~30, Crawler Laser 120.
  "rayWidth": 0.5        beam thickness (it's a CIRCLE cast, so a fatter
                         beam lands easier but snags on scenery sooner).
  "damageRepeatDelay": 0.25   seconds before the SAME target can be hurt
                         again while you hold the beam on it. This IS the
                         laser's damage rate - lower melts faster.
  "layerMask": "Entities"     what the beam can hit AND stop on. Use
                         ["Entities","Ground"] to have terrain block it;
                         Entities alone shoots through walls. (The
                         "phasing" option simply strips Ground from this.)
  "visual": "..."        the beam's look - swap in another laser's visual
                         prefab by name.

  CUSTOM BEAM ART ("beam" block) - your own sprites on the beam.

  HOW A BEAM IS DRAWN, because it decides what is possible. A beam is ONE
  SINGLE STRETCHED QUAD. Every frame the game puts a SpriteRenderer at the
  barrel, rotates it toward wherever the ray landed, and sets its WIDTH to
  the whole distance. One sprite, one rectangle, muzzle to target.

  Two consequences:
    * A beam CANNOT BEND as it stands - there is nowhere for a curve to
      live inside a single quad. A bending beam has to be a CHAIN of short
      quads, which is a separate feature built on top of this one. This
      block is the foundation it needs: loading and placing beam art.
    * A beam CANNOT ANIMATE by flipbook. Use "tiling": "repeat" for the
      illusion of movement instead.

  THE PIVOT TRAP, HANDLED FOR YOU. Every stock beam sprite has its pivot
  on the LEFT EDGE, because the quad grows rightward from the muzzle. The
  Sprite Sheet Builder writes a CENTRED pivot - right for a bullet, wrong
  for a beam, and it would hang half the beam out behind your ship. The
  mod rebuilds your sprite with a left pivot automatically, so ONE sprite
  works as both a bullet and a beam and you never touch the manifest.

  Draw beam art pointing RIGHT, as a horizontal strip.

      "beam": {
        "sprite": "myBeam",
        "tiling": "repeat",
        "thickness": 0.8,
        "warmupSprite": "myCharge",
        "warmupThickness": 0.4,
        "impactSprite": "mySparkAnim",
        "impactFps": 0,
        "glow": false,
        "material": "SpriteUnlitAA",
        "offset": 0.2
      }

  Shorthand: "beam": "myBeam" just re-skins the firing beam.

    sprite      the firing beam. A name from your "sprites" folder or any
                sprite in the game (custom searched first). The stock ones
                are Sprite_Lazer_6_0 .. _6_0_3 - all tiny 8x8 px, because
                they get stretched. An animation only uses frame 1 (logged).
    TWO TRAPS WITH "repeat", both of which look like a broken beam:
      1. The stock beam sprites are 8x8 GRADIENTS drawn to be stretched, so
         repeating one just makes a stripey mess. "repeat" only makes sense
         with your own seamless art. The mod warns if you use it with the
         template's sprite.
      2. Tiled draw mode fills the size by repeating in BOTH AXES. So a
         "thickness" taller than your sprite stacks it VERTICALLY - THIS IS
         WHAT LOOKS LIKE "TWO BEAMS". thickness 0.8 with a 0.4-unit-tall
         sprite gives exactly two stacked beams. In repeat mode the thickness
         comes from your ART: at 20 px per unit, a 16 px-tall sprite is 0.8
         units, so draw it taller for a thicker beam. Leave thickness blank
         and the mod matches the sprite for you; set it anyway and it warns
         with the number your sprite actually wants. With "stretch" none of
         this applies and thickness is free.

    tiling      "stretch" = what every stock beam does, one sprite pulled
                from muzzle to target, so an 8px sprite becomes a smooth
                gradient.
                "repeat" = tiles the sprite along the beam at its true
                size, so a SEGMENT of art repeats over and over. This is
                the one for a beam made of visible chunks, links or
                chevrons, and it is what makes a beam read as flowing
                rather than static. Needs art that tiles seamlessly
                left-to-right.
                ("simple" is refused: that draw mode ignores the
                renderer's size, and size is the only thing making the
                beam reach its target, so you would get a stub at the
                muzzle.)
    thickness   visual thickness in world units. Stock beams are 0.4; the
                Crawler's is 1.5. This is VISUAL ONLY - "rayWidth" is the
                separate HIT thickness, and the two want to stay roughly
                in step or the beam looks like it misses.
                projectileScale also scales this if you would rather
                multiply than set.
    warmupSprite / warmupThickness
                the thin beam shown while CHARGING, before the shot fires
                - only visible with a "warmupTime". Separate renderer and
                sprite; the stock ones are all tiled, thickness 0.4.
    impactSprite / impactFps
                the spark where the beam lands. This one IS a particle
                system, so unlike the beam itself it CAN animate - name an
                "...Anim" and every spark plays the whole flipbook. Blank
                impactFps spreads the sequence over each spark's lifetime.
    glow        EVERY stock beam uses the emissive shader
                (EmissiveUnlitSprite), which suits a glowing energy bar but
                blows detailed art out toward white. If your custom beam
                looks washed out, set false - same fix as projectileGlow
                for bullets.
    material    escape hatch. The three in play are EmissiveUnlitSprite
                (stock), EmissiveUnlitSpriteBright (the Crawler's) and
                SpriteUnlitAA (as painted). Overrides glow.
    offset      extra length past the hit point, and how far the spark
                sits beyond it. Stock 0.2 on all four beam prefabs. Raise
                it if your art has a soft or capped end; drop toward 0 for
                a beam that stops exactly on the target.

  TERRAFORMING BEAM (cellConvertData) - a hidden feature. The beam
  CONVERTS TERRAIN where it lands. Only one weapon in the game uses it:
  the Crawler Laser (radius 4, eats 10 different cell types).
      "cellConvertData": {
        "enabled": true,
        "radius": 4,
        "convertableCells": ["CellType_Mud", "CellType_Moss"],
        "resultCellType": "CellType_Mud"
      }
    convertableCells   which terrain it may eat (one name, or a list).
    resultCellType     what it turns into. Point it at a soft/empty cell
                       to dig tunnels, or a solid one to BUILD walls.
    Cell names include CellType_Mud, CellType_Moss, CellType_Blob,
    CellType_Hazard, CellType Bark, CellType Gold, CellType Fog Steam.
    NOTE cellConvertData exists on every weapon but ONLY hitscan runs it.

WHAT WORKS on a beam:
  damage, BURN (yes - a beam does apply burn), damageRepeatDelay, range,
  rayWidth, layerMask, visual, pushForce, cellConvertData, warmupTime,
  cost / fireRate, aimAssistData, plus Weapon Forge's electric options
  (dischargeOnFire, lightningColor, lightningRange) and "phasing".

WHAT DOES NOTHING on a beam (there is no projectile to carry them):
  projectileSpeed / projectileCount / projectileRadius, spread and angle
  options, rangeData, lifetimeData, impactBehaviour, homingData,
  piercingData, projectileBounceData, movementNoiseData, rotationData,
  subEmitter, and the custom wave / orbit / turret options.
  The "explosion" and built-in "discharge" blocks also do nothing on their
  own, because a beam never runs the impact code that triggers them - use
  "dischargeOnFire": true for chain lightning instead.

----------------------------------------------------------------
 6e. MINION SPAWNERS (pets / drones) - WHAT APPLIES
----------------------------------------------------------------

A minion spawner does not fire anything - it SPAWNS A UNIT that then
lives and fights on its own AI. So the spawner's stats barely matter;
nearly everything about the pet comes from the unit prefab you choose.

  "minionPrefab": "Enemy_Fly Variant Drone Electric"
        WHICH pet to spawn - the field that actually matters.
  "projectileSpeed" / "projectileSpeedVariance"
        how hard the pet is flung out as it appears; it flies under its
        own power afterwards.
  "minionFacesShootDirection": true
        spawn it already facing the way you fired.
  "velocityInfluenceData": { ... }
        your ship's movement adds to the launch (see 6b for the fields).

THE DRONES (what the in-game drone gadgets summon):
  Enemy_Fly Variant Drone            - Caps drone (gun)
  Enemy_Fly Variant Drone Electric   - Electron drone (electric)
  Enemy_Fly Variant Drone Missile    - Purple drone (missiles)
  Enemy_Fly Variant Drone Phantom    - Phantom / tech drone
  Enemy_Fly Variant Drone Suicide    - kamikaze drone
Other spawnables: Unit Mine FloaterOfficerCaps, Enemy_Cross Variant Pin,
Unit Cross OneShot 4, Enemy_Child.

WHAT WORKS: minionPrefab, projectileSpeed(+Variance),
minionFacesShootDirection, velocityInfluenceData, and the trigger-side
stats - fireRate, cost / resourceUsed, burstSize / burstDelay,
projectileCount (spawn several at once), spread + angle, warmupTime.

WHAT DOES NOTHING: damage, burn, explosion, discharge, pushForce, and all
projectile options (rangeData, lifetimeData, impactBehaviour, homingData,
piercingData, bounce, movementNoise, rotation, subEmitter) - no projectile
is ever created to carry them. The pet's own damage, health and weapon
live on its unit prefab and are NOT editable from JSON.

THE DRONE GADGETS ARE A DIFFERENT TYPE: the drones you pick up in-game
(Module Active Drone Caps / Electron / Purple / Phantom / Suicide) are
SpawnMinionModuleData - they hold a UNIT, not a weapon. Weapon Forge
cannot use them as a template; the build is skipped with a "no weapon"
error. To build your own drone launcher, use a minion-spawner weapon
template above and point minionPrefab at the drone you want.

----------------------------------------------------------------
 7. MIXING AND MATCHING
----------------------------------------------------------------

Because asset references are looked up by name, you can combine
parts of different weapons:

  - Popper stats with the Dart's missile model:
      "template": "Module Weapon White Popper",
      "weapon": { "projectilePrefab": "<dart projectile name>" }

  - A shotgun that fires homing pellets:
      "template": "Module Weapon White Shotgun",
      "weapon": { "homingData": { "enabled": true,
                  "targetMode": "AutoSeekWhenShot",
                  "acceleration": 15, "torque": 250 } }

  - A rifle whose shots explode AND chain lightning on impact:
      "weapon": { "impactBehaviour": { "enabled": true,
                    "spawnExplosion": true, "discharge": true },
                  "explosion": { "radius": 1.5, "damages":
                    [ { "amount": 3, "damageType": "White" } ] },
                  "discharge": { "chainLength": 4,
                    "subSystem": "Player",
                    "damage": { "amount": 2,
                                "damageType": "White" } } }

Exact prefab/asset names come from an AssetRipper export of the
game - the file names ARE the asset names (drop the .asset/.prefab
extension).

----------------------------------------------------------------
 8. THE MODULE CARD ("module" BLOCK)
----------------------------------------------------------------

Optional block that changes how the weapon's module looks in the
grid/inventory UI and what it grants when equipped:

  "module": {
    "displayName": "MY GUN MK II",   Card title (defaults to the
                                     top-level displayName)
    "description": "...",
    "level": 2,
    "icon": "HUD_GridTiles_8",       Module card icon. These are the
                                     weapon icon sprites; the builder
                                     page has a dropdown that picks one
                                     by weapon name. A few: Popper 13,
                                     Bolt 1, Dart/Rocket 29, Shotgun 7,
                                     Laser 8, Air Mine 25, Drone 19.
    "color": "ColorPurple",          Card color tint - a game
                                     ColorAsset name OR a hex value
                                     like "#7fd4ff" (a new color is
                                     created on the fly).
    "resourceGain": {                Change which resource (and how
      "resource": "Resource White",  much) equipping this weapon
      "amount": 12                   adds to your ship. Overrides
    },                               the template's bonus (e.g. the
                                     Caps Laser normally grants
                                     orange/caps capacity).
                                     NOTE: do NOT use "Resource Money"
                                     (or any shared/currency resource)
                                     here - the game manages those
                                     run-wide, so a per-weapon Money
                                     gain is ignored (it would hang
                                     loading). Money is fine as a
                                     "resourceUsed"/"damageType" though.
    "powerNodes": 6                  How many power cores can attach to
                                     the module (the "0 / N" cap in the
                                     grid). A number = fixed; or a range
                                     { "min": 4, "max": 8 } to roll
                                     randomly. Popper is normally 2-3.
  }

Game ColorAsset names:
  ColorWhite   ColorOrange   ColorPurple   ColorBlue
  ColorRed     ColorYellow   Color Tech    ColorPower

----------------------------------------------------------------
 9. RESOURCE NAMES
----------------------------------------------------------------

  Resource White      white / stamina
  Resource Caps       orange / caps
  Resource Purple     purple
  Resource Electron   electric / blue
  Resource Health     red / health
  Resource Money      yellow / money  (SHARED - see note below)
  Resource Fuel       fuel
  Resource Tech       tech

"Resource Money" is shared/currency and is NOT usable as a weapon
resource at all - not "resourceUsed" (ammo), "resourceGain", or
"damageType". Any of them hangs/breaks the game, so Weapon Forge
ignores/reverts Money and logs a warning. Use one of the others.

Shorthand works too: "damageType": "White" finds Resource White.
Resources decide BOTH what ammo you drain (resourceUsed) and what
damage color/type you deal (damageType) - they don't have to
match.

----------------------------------------------------------------
 10. TROUBLESHOOTING
----------------------------------------------------------------

Weapon doesn't appear on the loadout screen:
  - Check BepInEx\LogOutput.log for "WeaponForge" lines. A
    missing "name"/"template" or a typo'd template name is
    logged with your file's name.
  - Two files with the same "name" - only the first loads.
  - JSON syntax error (missing comma, quote). Paste the file into
    an online JSON validator.

A stat change didn't apply:
  - Restart the game fully - files are read at menu load only.
  - Check the log for a "does not match any field" warning: the
    field name may be misspelled, or it belongs to a different
    weapon type than your template.
  - A few game fields have intentionally odd spelling, e.g.
    "multiplyer" - copy names from this guide exactly.

Weapon appears but is silent / invisible projectiles:
  - You probably swapped in an sfx id or prefab name that doesn't
    exist. Remove the override to fall back to the template's.

What JSON canNOT do (yet):
  - Import brand-new art or sound files from outside the game.
    You can only reference assets that already exist in PUNK.
  - Make weapons drop in-game / appear in shops. Planned for a
    future version.
  - Invent behavior no game weapon has (e.g. a true black-hole
    gun). Stats and combinations only - new mechanics need C#.
